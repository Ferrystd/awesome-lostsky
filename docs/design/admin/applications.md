# 后台应用与页面规则

本页登记应用专属边界和页面例外；未登记的行为必须服从公共规范。

## Team、Shop 与 Transaction 工作台概览

1. **范围**：Team、Shop 与 Transaction 的团队工作台和个人工作台侧栏、移动端主导航及对应概览路由；Chat、商城顾客中心和公开页面不适用。
2. **行为**：六个工作台都必须把“概览”固定为首个导航入口，并绑定本工作台的概览路由；禁止隐藏、改名、改绑到具体业务列表或按 Permission 移除。团队模式与个人模式各自保留独立概览，跨应用进入个人模式时落到目标应用个人概览。
3. **实现**：沿用 `TeamShell`、`ShopManageShell` 与 `TransactionShell` 的现有导航数据和 `House` 图标；团队概览分别使用 `/`、`/manage`、`/overview`，个人概览分别使用 `/personal`、`/manage/personal`、`/personal`。Team 团队概览保留既有实现；其余五个概览统一使用 `LsWorkspaceOverview`，在主视觉中提供对向工作台入口，不新增应用下拉或分段式切换控件。
4. **适配**：桌面侧栏与移动端导航共享同一数据源；“概览”保持至少 44px 触控高度、可见键盘焦点、可读链接名称和当前路由状态。文本放大时允许标签自然占用既有导航空间；概览切换不增加动效，减少动态无额外例外。
5. **状态**：概览不要求具体业务 Permission；加载或摘要错误只影响身份、团队等摘要文字，不移除工作台操作或业务入口位置。缺少业务 Permission 时，概览仍可访问，具体业务入口保持可点击说明的禁用态，不在卡片内常驻权限错误；点击后由全局提示说明原因且不进入业务路由。概览只读取既有访问快照，不请求订单、流水或统计数据。Transaction Ability 缺失时继续使用全应用不可用页，不把个人概览作为绕过 Ability 的入口。
6. **例外**：Transaction 团队概览保留 `/overview`，避免改变既有 `/` 流水深链；除此之外无例外。
7. **验收**：Vitest 静态契约断言三个壳层的团队与个人导航首项均为“概览”且无 Permission；Playwright 分别验证团队/个人概览可达、无权限时不发受保护业务请求，并在桌面与移动端确认导航可见；发布前运行类型检查、相关 E2E、文档构建和完整静态构建。

三个业务工作台的侧栏底部都只保留“退出登录”这一全局会话操作。入口必须保持至少 44px 触控高度，并与同栏导航图标、文字左对齐；桌面固定侧栏与移动抽屉沿用同一结构和 `NButton` 键盘行为，不得因组件库默认居中样式改变位置。加载、空、错误、Permission 和 Ability 状态均不隐藏该入口。验收以源码契约和三个已登记壳层的真实组件预览确认，并在 Shop、Transaction 的工作台 E2E 中读取实际 `justify-content`。

## Team

- Team 团队工作台不得因双工作台架构重排既有顶栏、侧栏、概览卡片或内容区。概览深色主视觉只把“进入消息”改为“进入个人工作台”；顶栏右侧只把原动作替换为团队、商品、记账和聊天四入口。Team、Shop 与 Transaction 均禁止使用应用下拉或分段式工作台切换控件。
- Team 个人工作台侧栏底部不提供“切换身份”入口；身份领取与切换仍由 Account 身份页处理。退出入口遵循上述三个业务工作台的统一契约，无例外。
- 实体、成员、顾客及所有候选项统一使用 `LsEntityIdentity`；媒体为圆角方形，真实头像优先。此前实体与成员分别使用圆形和方形不是巧思，而是没有语义依据、会破坏主体识别的一致性问题，不得恢复。
- 实体、成员、顾客、文件、文档、角色、虚拟实体、申请字段、通知、加入审核是集合页，必须有 `LsListToolbar`。
- 成员移动端以“管理/查看”为主操作，对话、预览、封禁、离职进入更多；危险操作不得成为主操作。
- 顾客列表不得再嵌套第二个 `LsPage`；通知和审核使用连续列表。
- 顾客详情在同一资料表单中使用 `LsEntitySelect multiple` 维护协作发单人，与其他顾客字段一次保存；不新增独立绑定页、二次确认或页面私有选择控件。只读状态仍显示现有协作 Entity。
- 实体、成员、顾客、文件、文档、角色、虚拟实体、对象字段、申请字段、通知、加入审核、资源页和团队设置的页面级无数据统一使用 `LsEmptyState`；创建入口仍位于页面标题，不进入空状态组件。
- 上传缺少 Ability 时只禁用文件选择，不显示常驻错误。加入申请的动态文件字段统一使用 `LsUploadField`，其余动态字段使用对应 Naive UI 控件；缺失必填项时阻止提交并在字段区域说明，不得让协议字段回退到页面级原生控件。
- 加入申请页仅在链接包含有效邀请参数时，以非输入控件只读确认当前邀请人，不允许申请人改写链接带入的来源；没有邀请参数时不得渲染邀请人区域，页面结构与引入该功能前保持一致。成员详情将加入时间与邀请人放在独立的成员信息区，邀请人必须按全局 Entity 展示并明确标注其他团队来源。
- Team 成员、个人资料与实体详情复用 `EntityProfileFields`；其中单文件资料上传统一交给 `LsMediaUploadField`。Team、成员与虚拟实体本人编辑位于 Team 个人工作台，并复用公共字段与权限卡片。Team Entity 的字段和业务内容按类型与参与关系受限；身份领取留在 Account，顾客资料留在商城顾客中心。文档、文件和资源目录的行内动作统一使用 `LsResponsiveActions`；文件与文档分页统一使用 `NPagination`。
- 文档编辑页的 `LsMarkdownEditor` 是第三方编辑器实现级例外：保留其原有的模式切换、候选项与工具栏视觉结构，不将 `NRadioGroup`、`NButton` 或 `NInput` 的通用皮肤套入编辑器内部。页面其余字段仍使用标准 Naive UI；验收时确认编辑器模式、源码与对象候选项和统一化前版本一致。
- 文档创建/编辑页的文档标签与实体资料管理页的公开文档分组统一使用 `LsFormList`。两处都允许添加、删除、拖拽及按钮排序，并按顺序提交；标签错误必须就近阻止保存。公开文档分组只出现在 Team、Member 和 Virtual 实体，Customer 不显示；缺少 `team.entity.profile.manage` 时展示只读内容并禁用列表变更，不发写请求。
- 团队设置各应用分组的保存动作统一使用 `SettingsSaveButton`：桌面端固定为紧凑的 `9rem` 等宽按钮，小于 640px 时铺满标题动作区。宽度由该 Team 业务组件内部持有，不得由设置页面穿透、传参或复制 CSS；其他 `LsButton` 与 `LsSectionHeader` 动作不继承此等宽规则。

### Team 资料表单尺寸

1. **范围**：Team 实体资料页、顾客详情页及其使用的 `EntityProfileFields`、`LsMediaUploadField`；列表、设置页和商城顾客中心不适用。
2. **行为**：实体资料表单中的命令必须紧凑且由所属语义组件统一管理：上传命令在各媒体字段中等宽，添加和保存不得被页面拉长；不同任务不为视觉齐边强制等宽。顾客详情与实体详情的摘要、资料面板和字段使用同一个 `form` 页面宽度，禁止用更宽面板包住窄表单形成无用途留白。
3. **实现**：`LsUploadField` 在自身语义内固定紧凑上传命令，`LsFormList` 与 `LsFormActions` 的添加/保存命令按文案自适应并保持最小触控宽度；不同任务不共享全局等宽令牌。实体资料页与顾客详情页只组合这些语义组件，不得穿透内部节点或传递视觉参数。两页均使用 `form` 容器，表单字段继续使用 `LsField` 与 Naive UI 控件。
4. **适配**：小于 640px 时上述按钮改为容器满宽，资料字段保持单列，320px、200% 文本缩放及长 URL 不得产生横向滚动；键盘、读屏和焦点顺序不因宽度调整而改变，减少动态不适用。
5. **状态**：默认、禁用、上传中、保存中及权限只读状态保留相同宽度；读取错误和加载骨架仍占用当前页面容器，不切换为宽容器；空状态不适用于详情资料表单。
6. **例外**：顶栏对话入口不属于表单命令组，保持内容自适应宽度；资料页设置动作必须进入 `LsFormActions`，无页面级尺寸例外。
7. **验收**：组件测试锁定上传局部固定宽度、添加/保存内容自适应和移动满宽契约，源码守卫禁止页面穿透 `.ls-*`、直接 `NSwitch` 与开关轨道文字。Playwright 检查命令触控尺寸、不过长和移动满宽；源码契约锁定实体与顾客详情使用 `form` 宽度。实体详情把团队内可见与公开主页展示合并在唯一“可见性设置”面板，只保留一次原子“保存可见性”，并覆盖脏草稿、刷新保护和只读同构状态。`LsSwitch`、`LsSwitchField`、`LsMediaUploadField` 与 `EntityProfileFields` 真实组件预览覆盖相关状态，发布前运行前端测试、类型检查、文档构建及完整静态构建。

### Team 高级范围权限

1. **范围**：仅适用于 Team 角色详情的团队 Permission 配置和成员角色摘要；平台 Admin RBAC、成员直授及其他应用不适用。
2. **行为**：普通权限区将身份领取与指定实体 assume Permission 合并为默认折叠的“实体委托”，把虚拟实体维护放入“实体管理”，把仅限聊天的虚拟实体代操作放入“聊天”；“高级范围权限”按相同业务分组展示父键。每项显示父键、当前覆盖数量和可展开叶子清单；选择父键或通配符会清理草稿中被覆盖的子键，取消后不恢复已清理项。本次新增父键保存前必须确认范围。
3. **实现**：目录以服务端 `groups` 和 `advanced_items` 为事实源，前端不得手输或推测未知键；加载只呈现服务端原始集合，点击保存时才按分段前缀与 `*` 规则提交最小 `permission_keys` 集合。服务端保存不同合法键时不做覆盖归并。成员页只分配角色，摘要逐条显示存储记录，并把实体委托父键留在平级“实体委托”组内同时标记“高级范围”。
4. **适配**：沿用后台单列、连续分隔列表与 Naive UI 控件，交互目标至少 44px；320px 下键、文案和数量可换行且不得横向溢出。折叠、搜索、复选框、叶子详情和确认弹层均可键盘操作、具有可读名称与可见焦点；不新增装饰动效。
5. **状态**：目录加载、保存错误和只读状态沿用角色详情现有反馈；空高级目录显示明确空结果，搜索无结果不影响已选草稿。被更宽父键覆盖的叶子与较窄父级显示覆盖来源并禁用；保存中锁定重复提交，取消确认返回原草稿。
6. **例外**：精确实体委托目标仍默认添加叶子权限，仅把其合法父键加入高级目录；`chat.virtual.<slug>.act` 直接列在“聊天”组，不进入实体委托目标编辑器。查看摘要不归并跨角色重复、父子或通配符与指定 slug 记录。拥有 `team.role.write` 者可配置当前团队完整目录，不要求自身拥有目标业务 Permission。
7. **验收**：Vitest 覆盖精确、父级、通配、兄弟匹配和父子去重；Playwright 覆盖选择 `team.ability`、二次确认、角色分配后入口可用，以及桌面、320px 与键盘操作；后端锁定目录生成、团队边界和即时生效。发布前运行后端权限测试、OpenAPI 路由测试、类型检查、完整 E2E、文档构建和静态构建。

### Team 成员离职

1. **范围**：Team 的 `/members` 与 `/member-edit`，用于具有 `team.member.remove` 的管理员办理成员离职；成员本人的自助离队申请不在此规则范围。
2. **行为**：管理员操作必须显示为“离职”，确认后直接把成员设为已离队并使现有会话失效，不得为管理员创建待审离队申请。资料、角色、对象标识、业务关系与任期历史必须保留，Team owner 不得离职。
3. **实现**：列表使用 `LsResponsiveActions` 的危险操作，详情管理区使用 `LsButton variant="danger"`；两处统一调用 `POST /memberDeparture/depart`，成功后刷新成员列表和详情并通过全局反馈显示“成员已离职”。
4. **适配**：桌面端显示图标与“离职”文字；移动端收入更多操作，不取代“管理/查看”主操作。键盘、触控、读屏和文本放大沿用公共按钮与响应式操作组；确认文案必须同时说明会话失效与历史保留，不依赖颜色传达风险。该操作不包含动效，减少动态不需要额外例外。
5. **状态**：请求期间按钮显示加载并阻止重复提交；成功后成员显示“已离队”且不再显示离职入口；失败时保留当前页并显示服务端原因。缺少 `team.member.remove` 时列表入口保持禁用并说明 Permission，详情不显示危险区；加载与空数据不产生该操作。
6. **例外**：成员本人仍按 `member.departure_mode` 使用自助申请、取消和审核流程；这是成员主动离队与管理员办理离职的责任边界，不允许扩展到其他危险操作。
7. **验收**：Vitest 锁定两个管理员入口的“离职”文案、`/memberDeparture/depart` 请求与旧“发起离队申请”文案移除；后端成员生命周期测试确认一次操作直接生成已批准记录、关闭任期且保留 Entity。发布前运行 `npm test`、`npm run typecheck`、Team E2E、完整静态构建与文档构建。

### Team 申请字段管理

1. **范围**：Team 的 `/join-fields`、`/join-fields/new`、`/join-fields/:id`，用于团队管理员维护加入申请表结构和审批后转存规则。
2. **行为**：列表必须同时展示启用和停用字段，并支持按名称/标识搜索及按启用状态筛选；创建、查看和编辑使用独立路由。字段标识创建后只读；删除已有提交记录的字段必须失败并提示改为停用。禁止在列表中常驻编辑器、隐藏停用字段或把字段排序改为仅支持拖拽。
3. **实现**：列表使用 `LsListToolbar`、`LsEmptyState`、`LsAsyncState` 与连续边界；表单使用 `LsField`、`LsFormList`、Naive UI 控件、`LsInlineError` 和 `LsButton`。选项以有序的“显示名称 + 提交值”编辑并兼容历史字符串或对象格式；完整布尔设置使用 `LsSwitchField`，紧凑布尔控件使用 `LsSwitch`，状态使用 `LsStatusTag`，动效只使用公共令牌。
4. **适配**：桌面与移动端均为单列任务流；320px 下工具栏、选项和命令按钮纵向排列，交互目标不小于 44px。键盘可完成搜索、筛选、选项增删排序、保存和删除确认；文本放大后标签与说明自然换行；减少动态时取消列表位移。
5. **状态**：首次加载显示结构骨架，无字段与筛选无结果使用不同文案，读取和写入错误只在对应区域显示。`team.join_field.read` 控制列表和详情读取，`team.join_field.write` 控制创建、保存、删除及转存候选；只有读取权限时详情为只读模式，已知缺少权限时不得发起受保护请求。停用字段保留历史值并可重新启用。
6. **例外**：转存候选通过申请字段专用接口读取，只暴露当前团队人员 Entity 字段摘要，不额外要求 `team.entity.field.manage`；这是为了保持 `team.join_field.write` 已有的完整转存配置语义。除此之外无例外。
7. **验收**：Vitest 检查公共组件与导航契约；Playwright 覆盖启用/停用列表、选项校验、转存选择、只读权限和零越权请求，并在 320、375、768、1024、1440px 检查无横向溢出；后端测试锁定管理列表与公开表单的不同过滤范围。

## Shop

- Shop 管理后台保留既有深色侧栏、页面标题和业务内容区；顶栏只把原“查看商城前台”动作替换为团队、商品、记账和聊天四入口，不增加应用下拉或个人/团队分段控件。
- `/manage` 团队概览以“进入个人工作台”进入 `/manage/personal`；个人概览以“进入团队工作台”返回 `/manage`，“我的商品”和“我的业务订单”保留为独立业务入口。两个概览都使用公共概览组件，入口不因 Permission 隐藏，受保护业务仍由路由与服务端按 Permission 拦截。
- 个人工作台侧栏在“概览”后固定显示“我的服务”“我的权益包”“我的卡活动”“我的商品”和“我的业务订单”；前四项统一受 `shop.product.self.manage` 保护，缺少权限时保留禁用态并说明原因，且不得发起对应业务请求。
- 本人商品页复用团队商品的列表、表单和核销字段组件，但必须使用 personal scope API 与返回路径；表单不显示可编辑的专属 Entity 选择，只显示“自动归属当前 Entity 且不可转移”的只读说明。编辑页把核销字段放在商品字段下方，标题区只保留使用 `LsPagePrimaryAction` 的“预览前台”，上下架统一由正文“上架状态”控制。

### Shop 服务计量规则

1. **范围**：Shop 管理后台 `/manage/services/new` 与 `/manage/services/:id` 的“计量规则”，以及 Team 设置中的“服务履约”默认值；权益包、核销表单和权益快照均从各自步长推导显示精度。
2. **行为**：用户只配置计量单位与最小核销步长，不再单独配置数量精度。系统必须按步长有效小数位自动推导精度，例如 `1 → 0`、`0.5 → 1`、`0.25 → 2`、`0.0001 → 4`；履约数量仍必须是步长的整数倍。
3. **实现**：服务表单固定使用 `LsField` 与 Naive UI `NInputNumber`，步长最多输入四位小数；服务端使用 `ServiceQuantity` 从步长推导校验精度，前端使用共享数量工具从响应中的步长推导显示精度。数据库、模型、请求与响应均不得出现独立的 `quantity_scale`，也不得新增精度选择器、页面私有控件或父级样式穿透。
4. **适配**：桌面与移动端保持“计量单位 → 最小核销步长”的单列顺序；提示文字说明精度自动确定，键盘、焦点、读屏、320px 与 200% 文本放大沿用 `LsField` 和 `NInputNumber` 契约，无额外动效。
5. **状态**：新建服务读取团队默认步长，编辑服务显示已保存步长；空值、零值、负值、超过四位小数或格式无效时禁止保存并由服务端返回可恢复的 422。权益继续使用领取时冻结的单位与步长，不被后续服务编辑追改。
6. **例外**：无。项目处于开发阶段，本规则不保留旧字段、旧请求或旧响应兼容层。
7. **验收**：后端测试覆盖四种代表步长、无效步长和非步长倍数；前端源码契约禁止服务表单、Team 设置、类型与响应消费重新出现独立精度字段，并运行类型检查、服务核销回归、文档构建和完整静态构建。

### Shop 服务默认金额分配

1. **范围**：Shop 管理后台 `/manage/services/new` 与 `/manage/services/:id` 的“默认单位金额与分配”；权益包、订单和历史履约快照不适用。
2. **行为**：单位服务价值或单位成本变化时，接单、发单与客服分配必须按当前团队“服务履约”的默认比例即时重算；团队分配始终取服务价值扣除成本和三项人员分配后的余额，禁止直接编辑。用户仍可在自动重算后调整三项人员分配，团队余额必须同步变化且金额不平衡时不得保存。
3. **实现**：字段固定使用 `LsField` 与 Naive UI `NInputNumber`；金额以分为单位计算并沿用权益包的向下取整规则，舍入余数归团队。页面提交完整金额快照，服务端忽略顾客端团队分配并再次计算余额；不得新增页面私有控件、视觉参数或父级样式穿透。
4. **适配**：桌面与移动端保持“价值 → 成本 → 接单 → 发单 → 客服 → 团队”的单列顺序；只读团队分配保留可见标签、数值和禁用语义，键盘跳过该控件，320px 与 200% 文本放大不得横向溢出。无额外动效。
5. **状态**：团队默认比例未返回前使用配置默认值；编辑页首次水合保留已保存的人员分配，只有用户随后修改价值或成本才按当前比例重算。空值、非有限值、成本高于价值或人员分配超过可分配金额时禁止保存；查询、权限和保存错误沿用现有页面状态。
6. **例外**：允许用户在自动重算后手工覆盖接单、发单与客服金额，以支持单个服务的特殊分配；团队金额没有例外，始终只读并由余额生成。
7. **验收**：Vitest 覆盖团队比例、分币舍入和团队余额；后端测试断言伪造的团队金额不会入库且负余额被拒绝；类型检查与完整静态构建验证禁用态和可空数字模型。

### Shop 普通商品默认金额分配

1. **范围**：Shop 团队与个人商品新建、编辑页中普通商品的售价、成本与默认分配；权益包计价汇总不适用。
2. **行为**：售价变化或成本变化时，接单、发单与客服分配按当前团队“服务履约”的默认比例即时重算；团队分配始终取售价扣除成本和三项人员分配后的余额，禁止直接编辑。三项人员金额允许在自动重算后手工覆盖，订单创建时冻结商品当前金额。
3. **实现**：复用 `calculateDefaultServiceDistribution` 与 `calculateServiceTeamCut`，金额以分为单位向下取整且余数归团队；团队与个人商品候选接口都必须返回 `service_defaults`。字段固定使用 `LsField` 与 Naive UI `NInputNumber`，不得新增页面私有控件、视觉参数或父级样式穿透。
4. **适配**：桌面与移动端保持“售价（销售与履约）→ 成本 → 接单 → 发单 → 客服 → 团队（默认分配）”的单列键盘顺序；只读团队分配保留标签、数值、禁用语义和余额说明，320px 与 200% 文本放大不得横向溢出。
5. **状态**：新建页在团队默认比例返回后立即计算；编辑页首次水合保留已保存的人员分配，用户随后修改售价或成本时重算。空值、非有限值、成本高于售价或人员分配超过余额时禁止保存；权益包计价锁定时沿用只读汇总。
6. **验收**：Playwright 覆盖成本分组、售价和成本触发重算、团队只读余额及提交快照；类型检查、Shop 管理回归与完整静态构建必须通过。

### Shop 权益包服务项布局

1. **范围**：Shop 管理后台 `/manage/packages/new` 与 `/manage/packages/:id` 的“服务权益”重复项；服务定义、商品表单、卡活动和商城前台不适用。
2. **行为**：每项服务默认先显示可扫描摘要，摘要至少复述服务、额度、有效期和单位价格；用户展开后按“额度 → 价格与成本 → 固定分配 → 团队余额”完成单列任务。选择服务时继承服务金额，修改价格或成本后按团队默认比例重算固定人员分配，不显示分配方式或比例输入。行操作只能占用项目头部，不得形成贯穿整项高度的右侧栏压缩表单。禁止把九个字段作为桌面三列矩阵，也禁止把所有高级金额字段永久同时展开。
3. **实现**：外层固定使用 `LsFormList`，字段固定使用 `LsField` 与 Naive UI 控件；页面仅保留业务摘要展开和三个具名组，组内始终为单列。`LsField` 统一控制控件满宽和提示归属，`LsFormList` 统一控制项目头部及内容跨列。不得新增宽度、紧凑、列数或移动堆叠参数，不得穿透公共组件私有节点。
4. **适配**：桌面与移动端都保持同一单列字段顺序；金额汇总可在桌面三列、768px 以下两列、480px 以下单列。320px、200% 文本放大和长服务名称下不得横向溢出；摘要在窄屏把金额移到第二行，键盘与读屏顺序保持摘要、额度、金额、分成、余额、项目操作的业务顺序，拖拽仍有上移/下移等价路径；减少动态沿用 `LsFormList`。
5. **状态**：新项目默认展开，既有可编辑项目默认折叠，冻结只读项目默认展开以保证禁用列表内仍可读；未选择服务、长提示、比例/固定金额和保存错误保持相同组序。加载由既有查询状态处理，空列表由 `LsFormList` 处理，缺少 Permission 时不进入该写入路由。所有数字输入都按 `number | null` 处理，空值与非有限值阻止保存，不得直接对表单模型调用 `toFixed()`。
6. **例外**：历史均摊权益包不显示金额与分成组，因为这些字段没有可编辑业务含义；除此之外无例外。
7. **验收**：Playwright 在桌面断言摘要可展开/收起、三个业务组的 `grid-template-columns` 均为单列、字段与实际控件等宽、项目内容不受操作区挤压；390px 断言摘要换行、字段等于项目内容宽度且页面无横向溢出。提交契约覆盖清空数量、价格、成本和分成时按钮禁用且不抛运行时错误；组件测试锁定 `LsField` 控件轨道和 `LsFormList` 跨列内容；再运行组件预览、类型检查、文档构建和完整静态构建。

### Account 登录页原生按钮例外

7. **验收**：`npm test` 的源码契约锁定仅这三个原生按钮；`tests/frontend.spec.ts` 在桌面和移动项目中断言两个 tab 数量为二且纵坐标一致，并继续检查两种登录表单均可操作；发布前运行 `npm run typecheck`、对应 E2E 与 `npm run build`。

- 顶栏固定提供四应用切换，但不显示个人/团队模式；Customer 继续留在消息与商城顾客中心，不进入后台双工作台。Customer 的商品项进入商城顾客中心，团队与记账项必须保留为带原因的禁用态，不得隐藏整个应用切换。
- 保留会话专属布局，不套用管理侧栏；根部使用统一主题，团队与参与者使用 `LsEntityIdentity`。
- 会话时间线可采用消息气泡，这是按发送者和时间组织内容的具名页面例外；气泡只能出现在消息时间线，不得扩展到会话导航、参与者或搜索结果。会话列表必须使用 `NButton` 驱动的连续分隔结构，键盘焦点与 hover 都只改变表面色，不浮起、不加新边框。
- 聊天团队选择页没有可用团队时使用 `LsEmptyState`。会话列表、未选择会话、空消息时间线和参与者详情都是聊天专属局部状态，保持紧凑布局，不使用页面级空面板。
