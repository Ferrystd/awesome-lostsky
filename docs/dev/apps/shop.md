# Shop 应用

Shop 同时承载团队的展示型商城和既有商家管理接口。访客通过
`https://{slug}.shop.lostsky.work` 浏览上架商品；顾客绑定后使用商家预存余额直接购买。
第一版不提供购物车、在线充值或第三方支付。

`/manage` 是 Shop 应用内的独立浅色后台，复用 LostSky 后台组件和权限语义，不改变公开商城的深色展示结构。管理入口统一为商品与订单，商品类型为普通商品、核销商品、卡密、套餐和多规格商品；核销配置与字段直接在商品表单保存，套餐和卡密直接选择商品。旧服务、权益包及活动模型仅作为内部配置复用，不再要求用户分步建立。Shop Ability 只参与开启 `shop.enabled` 和公开陈列/购买，未开通时仍可进入后台维护商品。

团队服务、权益包与活动接口位于 `/manage/*`，商品和订单接口分别位于 `/product*` 与 `/order*`；这些团队管理接口使用 `TeamWorkspaceAuth`，并复用 `shop.product.read/write/delete` 与 `shop.order.read/write`。服务、权益包和活动按当前团队隔离；兑换码列表不输出哈希、密文或明文，明文只能通过发行结果或显式查看接口获得。

## 业务职责

商品表单选项中的 `products` 返回已启用的商品候选及类型、归属和计价字段。个人选项只包含当前实体本人或团队公用商品；团队管理选项保留团队全量监管范围，最终组合保存仍校验父子商品归属，不允许引用其他实体的私有商品。

- 商品：列表、详情、创建、编辑、删除和接单人配置；商品封面与详情图片复用 Common 文件上传。
- 订单：列表、详情、创建、取消和完成，并由服务层处理相关交易与余额联动。
- Storefront：公开团队资料、上架商品列表和脱敏后的商品详情。
- 顾客业务：绑定当前商家的稳定顾客身份，在商城顾客中心维护资料、查询余额、订单、服务与卡密，并购买或取消自己的订单。
- 个人工作台：Team、成员和虚拟实体管理归属当前 Entity 的五类商品，并查看当前 Entity 作为接单人或发单人参与的业务订单；概览以当前 Entity 名称为主标题并同时显示类型与所属团队。组合只允许本人或团队公用商品，不允许其他实体私有商品。
- 团队工作台：所有后台 Entity 都可进入基础团队概览；商品、订单、服务、权益包和卡活动入口保持可达，数据和提交按 Permission 收口；受限按钮在点击时说明原因。顶栏直显五应用入口，个人模式由概览“进入个人工作台”进入并从顶栏“商品”返回。

## 鉴权边界

`GET /storefront*` 无需登录，团队由 `{slug}.shop.lostsky.work` 的请求上下文确定。公开商品必须同时满足 `shop.enabled=true` 与有效的 Shop Ability；关闭时列表为空，详情返回“商品暂未开放”。商品与商家订单入口接受四种有效实体 JWT，并经过
`TeamWorkspaceAuth`：本团队 Entity 可进入，外部 Entity 必须拥有目标团队至少一个角色，随后继续检查具体 Permission。`POST /customer/bind` 接受基础 User JWT 或任意有效 acting Entity，不使用
`TeamAuth`；其余顾客接口只接受属于当前团队的 `teamCustomer`。

| 领域 | 基础身份 | 额外限制 |
|---|---|---|
| 团队商品 | 四类有效实体，满足团队工作台访问条件 | 读取、写入和删除分别使用 `shop.product.read`、`shop.product.write`、`shop.product.delete` 权限 |
| 本人商品与权益资源 | Team、成员或虚拟实体 | `shop.product.self.manage`；所有读取和写入同时按团队与当前 `acting_entity.entity_id` 隔离 |
| 本人商品与服务调价 | Team、成员或虚拟实体 | `shop.product.self.reprice`；独立于 `shop.product.self.manage`，解锁本人商品、服务和权益包服务项的人员分成，以及公用服务项的价格、成本 |
| 订单 | 四类有效实体，满足团队工作台访问条件 | 读取要求 `shop.order.read`；创建、取消和完成要求 `shop.order.write`，创建另经过 `TransactionVerify` |
| Storefront | 无 | 仅返回上架商品和公开 DTO，不返回成本、分成或内部接单配置 |
| 顾客绑定 | 基础 User 或任意有效 Entity | 一个来源在同一商家只能绑定一个顾客；绑定不可转移 |
| 顾客中心 | `CustomerAccess` | 只能访问并维护当前商家的顾客资料、余额和订单；购买参数不接受顾客端价格与分成 |

跨模型的订单、流水和余额变更由服务层在事务中完成，控制器不负责数据联动。
新建核销商品与服务套餐订单同时冻结内部履约快照，额度、单位、步长、有效天数和分项金额按下单时配置发放，不随源配置后续变更。快照不对订单 DTO 输出；升级前无快照订单仍按原路径处理，卡密兑换目标快照尚在实施。
个人资源接口位于 `/personal/services*`、`/personal/packages*`、`/personal/campaigns*` 与 `/personal/products*`。服务、权益包和卡活动使用可空 `owner_entity_id`：空值表示团队公用，非空表示指定 Entity 所有；卡密继承卡活动归属。个人创建时服务端强制写入当前 Entity，编辑和停用不允许转移归属，也不提供硬删除；访问团队公用资源或他人资源的管理详情统一返回 `404`。每个写请求都必须提交 `expected_entity_id`，身份切换时返回 `409` 且不修改数据。

个人候选只包含本人和团队公用的已启用资源，其他 Entity 资源不可检索也不可通过接口引用；团队公用资源只能引用团队公用上游，本人资源可引用本人或团队公用上游。缺少 `shop.product.self.reprice` 时，本人商品与服务的新建人员分成由服务端按团队默认比例生成，编辑时沿用已保存的接单、发单、客服金额；本人售价与成本可改，团队分成始终取余额，负余额拒绝保存。本人权益包内所有服务项的人员分成沿用服务默认值或已有项目金额，公用服务项还锁定单位价格和成本；省略金额字段也不能触发下游重算。额度和有效期仍可调整，已被引用权益包的计价冻结继续生效。权益包只引用服务，服务套餐与卡密商品的分项金额由上游权益包强制汇总，不能直接覆盖。团队工作台继续由 `shop.product.write` 监管全团队资源。

升级执行 `sql/patches/20260909_shop_personal_reprice.sql`，将旧 `shop.product.self.package.reprice` 及其专用父键授权迁移到统一权限；旧键不作为运行时别名。
团队设置 `shop.sync_transaction` 默认开启；只有设置开启且团队具有等级不低于 1、未过期的 `transaction` Ability 时，新订单才自动生成关联流水。未同步流水不阻止订单创建，预存款扣减、余额日志与取消退款照常执行，订单和余额日志的 `trans_id` 保持 `null`。

发单人需要绕过销售订单直接给顾客补发、赠送或线下交付服务权益时，在 Transaction 的“赋予顾客权益”任务页选择 Shop 中已启用的核销商品或服务套餐商品。系统读取商品及权益包快照并直接生成 Customer 根 Entity 持有的独立权益，不创建 Shop 订单。`shop.sync_manual_entitlement_transaction` 默认关闭；开启后才按商品快照原子生成“服务包收款”流水。
有 `customer_id` 的订单使用顾客预存款支付；无顾客订单使用现金支付。商品默认分成是单件值并随数量缩放，显式订单分成是整单值；未显式给出团队分成时由总价减成本和其他分成后的余额补齐。

团队商品和本人商品表单都允许直接上传封面与 Markdown 详情图片。资源附件统一调用 Common `/upload`，使用团队 File 等级容量；未购买升级时仍有 0 级 128 MiB，商品保存继续由对应商品管理 Permission 校验，不额外要求 `file.upload`。容量用尽时保留 URL 输入，只禁用本地文件选择并说明具体原因。

顾客绑定同时创建零余额记录和不可搜索的 `teamCustomer` Entity。基础用户绑定保存在
`user_id`，外部 Entity 绑定保存在 `owner_entity_id`，两者严格二选一。派生顾客会话沿来源
Entity 的证明链实时重验；来源失效、会话撤销或顾客封禁后立即失效。

`GET /customer/me`、`POST /customer/me` 与 `POST /customer/slug` 是商城顾客中心的正式资料接口。Account 旧顾客自管深链会安全跳转 `/customer/profile`。顾客资料仍按团队隔离，昵称和简介不进入公开目录；新绑定顾客自动得到 slug，历史缺失标识可在商城顾客中心首次补全。

顾客下单在事务中锁定并复核商品、接单人和余额，金额全部由服务端计算。取消只允许订单所属
顾客操作处理中的订单；订单保留为“已取消”，关联交易被排除，预存余额和退款日志只写一次。

## 接口契约

多规格商品使用 `kind=5`，主商品只展示共同资料；`variants` 完整替换其隐藏规格，规格复用普通、核销、套餐与卡密类型。商城列表隐藏规格，购买与组成引用必须提交具体规格 ID。主商品停用后规格不可购买；规格独立定价与分成，嵌套继续沿用组合锁价规则。

商品和规格的 `purchase_fields` 定义购买资料；省略保留，空数组清空，多规格主商品不配置此字段。字段由服务端分配稳定 ID，订单以 `purchase_values` 提交 ID 到值的映射，每笔订单填写一份。服务端校验必填、类型和字段归属后，将定义与值保存到订单 `purchase_fields` 快照；后续修改或删除规格不改写历史资料。购买资料与核销字段相互独立。

商品创建接口支持 `kind=4` 与 `redemption` 对象一次创建核销商品，内部核销定义和权益明细与商品同事务保存。`redemption` 可配置单位、步长、每份额度、有效天数、自动结单时长、接单池及核销字段；自动结单时长为正整数分钟，`null` 表示关闭。价格、成本和分成只读取商品顶层字段，内部归属强制与商品一致。每份售价为整份额度的金额，不要求除以额度后仍能精确到分。编辑接口支持部分提交核销配置，省略保留原值；额度或有效期变更建立新的内部明细，保留旧明细 ID，已有订单继续使用快照。管理详情返回可回填的 `redemption`，前端统一入口由商品管理路由提供；已有普通商品不因此进入核销流程。

具体路径、筛选参数和响应结构见 [`shop.openapi.json`](../openapi/shop.openapi.json)。

## 权益与核销字段

商品可关联复用权益套餐，并声明普通商品、Ability 权益或可计量服务包。订单完成时由统一履约服务幂等交付 Entity 归属的服务权益；Customer 按实际数量创建履约切片。核销字段属于服务定义，不属于商品或权益包；因此同一商品包含的不同服务可分别配置自己的字段，同一服务被多个商品复用时保持一致。字段复用实体字段的类型与值校验，并增加“顾客发起时 / 核销接单时”填写阶段、顾客可见性和必填规则；新建字段默认在“核销接单时”填写，接单人只能在下单任务详情页填写并提交。字段定义只保存字段名称，字段值通过字段 ID 关联，已保存的切片字段值独立保留。

服务定义只配置计量单位与最小核销单位，数量精度由核销单位的有效小数位自动推导，最多四位；例如核销单位 `1` 使用整数、`0.5` 使用一位小数、`0.25` 使用两位小数。`quantity_step` 是数据库与接口中的唯一精度来源，不存储也不返回独立的 `quantity_scale`；已经领取的权益冻结领取时的核销单位，展示与校验均由该核销单位实时推导。

核销商品、规格和兼容服务定义配置两套独立超时规则，均接受 `1..5256000` 的整数分钟或 `null`（关闭）：

- `unused_auto_complete_after_minutes`：顾客购买完成、获赠或兑换实际发放权益时冻结到权益，并计算 `unused_auto_complete_due_at`。到期仅结算当前未使用且未预占的余量，不影响已发起任务或待确认邀请；后续取消或撤回释放的量由下一轮继续处理。它与 `valid_days` 的使用有效期独立。专用已结单切片标记 `settlement_kind=unused`，接单人为空；成本、发单和客服金额按权益冻结比例分配，原接单分成归团队。原始分摊保留作为防重复分配底账，展示实际分成使用 `settled_handler_cut` 和 `settled_team_cut`。Transaction Ability 有效时写类型 7“未使用权益结单”流水，现金、预存款均为零，不重复收款，也不形成接单人业绩；无 Ability 仍一致消耗权益。历史权益默认关闭，不追溯开启。
- `auto_complete_after_minutes`：接单人请求结单后顾客确认的时限。切片在发起、邀请接受或重新发起时冻结时长，实际请求时写入 `completion_requested_at`，到期时间为 `completion_due_at`；`started_at` 只记录实际接单，不触发自动结单。无请求的已接单任务也不会自动结单。顾客确认后才消耗权益并记录流水；顾客可填写原因拒绝，清空请求起点，继续履约、再次请求或申请取消。重复请求不重置时钟；重复确认仍检查顾客归属并保持幂等。`null` 时没有自动确认期限，但顾客与管理员仍可完成。

结单请求仍保持 `status=Processing`，通过 `completion_requested_at` 区分待确认。待处理取消或加价时不能请求结单；结单待确认期间不可加价、退回或改派，顾客如需取消应先拒绝结单再申请取消。管理者保留 `service.redemption.manage` 的人工直接结单权限。系统到期结单复核实际接单人及待处理事项，与顾客确认使用同一权益和实例行锁，记录无人员操作者的 `auto_completed` 事件。升级前接单时间不转化为结单请求时间，历史处理中任务需要接单人主动请求。

团队设置 `service.default_auto_complete_after_minutes` 只作为新建核销商品、规格和服务表单的顾客确认时限默认值；留空表示默认关闭。表单载入后用户可以清空或覆盖，编辑已有对象始终回填对象自身快照，团队设置刷新不得覆盖草稿。未使用权益时限新建默认关闭，不复用该团队默认值。

服务权益与履约切片是不同记录：Customer 可在同一权益下并行发起切片，由权益行锁防止超额预占；取消获批后释放预占数量。历史整数实例迁移保留实例 ID 并建立对应权益，不重建历史业务。计量模型不引入排班、竞价或服务二级交易。

团队服务定义中的默认单位金额以服务价值扣除成本后的余额作为分配基数。价值或成本变化时，接单、发单与客服金额按团队“服务履约”默认比例重算；三项人员金额仍可按单个服务覆盖，团队金额只读并始终取剩余值，服务端保存时再次计算以拒绝负余额和顾客端伪造的团队金额。

普通商品的“默认分配”使用同一套团队比例与分币规则：售价保留在“销售与履约”，成本与四项分配集中在“默认分配”；售价或成本变化时自动重算三项人员金额，团队金额只读并取余额。订单创建时冻结商品当前金额。服务套餐与卡密商品继续使用所选权益包的计价汇总。

团队新建服务权益包默认采用分项计价：每个服务项先显示服务、额度、有效期与单位价格摘要，展开后按“额度、价格与成本、分配”三个单列组编辑。选择服务时默认填入该服务已设置的单位价格、成本和固定人员分配；修改权益项价格或成本后，与服务表单相同，按团队默认比例重算接单、发单和客服的固定金额，团队分配取余额。权益包只保存固定金额，不提供分配方式。服务包商品的整包金额由权益项自动汇总；权益包被商品或兑换活动引用后，计价方式与服务项目冻结并默认展开只读内容。历史权益包继续按订单总额均摊，避免改变已存在的商品行为。新建服务成功后必须刷新管理候选快照，随后新建权益包应立即可选，无需刷新浏览器。

履约加价使用独立费用调整，商家提交前先核对顾客应付总额、内部成本和预计可分配金额，并在确认对话框复述顾客可见金额；费用必须由 Customer 确认后扣款，并在主履约完成时单独生成加价业绩。Customer 指定接单人时先创建持续等待的邀请，接受后才生成核销切片；对方处理前 Customer 可自行取消并释放预占，公开召唤会立即生成未分配的核销中切片。

服务编辑页把接单池与基本信息作为一次原子提交；兼容读写接口继续保留。名单仅允许当前团队有效的 Team、TeamMember 与 TeamVirtual Entity，留空表示不限制接单人；配置名单后，移除或排除的 Entity 会失去新邀请与公开任务资格，待确认邀请失效并释放额度，但不改写已经接取的历史任务。

Customer API 提供服务列表、详情、接单池、发起核销、申请取消，以及持有卡密的查询、领取和明文揭示。完整用户流程与边界见[Shop 应用说明](https://doc.lostsky.work/app/shop/)。
