# 后台页面组件化方法

本页是 Account、Team、Chat、Transaction、Admin、Weibo 与 Shop Manage 新增或修改页面结构时的组件化方法论。Site、Display 与 Shop 前台不强行并入后台视觉组件体系。

## 职责边界

- 页面负责路由、数据请求、权限与能力判断、业务编排，以及组件之间的顺序、网格、可用外部宽度和间距；页面可以决定组件放在哪个轨道、占多少外部空间，但不得进入组件内部重新分配控件宽度或排列。
- 组件负责自身视觉、固有尺寸、内部间距与排列、交互状态、响应式和无障碍语义。
- `LsPanel` 等基础组件负责卡片表面；页面不得在大卡片内重造已有控件的皮肤、对齐、状态或移动端规则。
- 跨后台应用复用进入 `@lostsky/ui`；同一应用多页面复用进入该应用 `components/`；单页面复杂区块可拆为业务子组件，但不得伪装成通用组件。

抽象依据是“同意图”，不是“同外观”。两个区块即使颜色相同，承担不同任务也不应合并；反之，同一业务意图即使当前样式略有差异，也应先收敛契约再迁移。

## 页面硬性分组规范

页面分组只按用户任务与信息关系决定，不按接口、数据库表、字段类型、前端组件类型或开发顺序决定。实施前必须为每个顶层组写出一个用户能理解的目标名称；无法命名的组不得创建。

1. **顶层依据**：同一用户目标、同一业务对象、同一权限范围和同一生命周期的内容必须进入同一顶层组；组内再按“理解现状 → 修改内容 → 确认结果”的任务顺序排列。
2. **拆分条件**：只有独立权限、独立风险或破坏性确认、独立异步状态、明显不同的业务对象，或需要单独分享/刷新任务时才允许拆为另一个顶层组。接口不同不是拆分理由。
3. **合并条件**：两个单项设置只要共享目标、权限和生命周期就必须合并；普通单个布尔项不得独占 `LsPanel`。同一目标的固定状态与可编辑状态必须留在同一组中，避免因实体类型变化而改变页面拓扑。
4. **容器数量**：一个 `LsPanel` 必须包含至少两个相关信息/控制项，或命中上述拆分条件；不得用面板代替间距，不得嵌套同义面板。连续内容优先使用标题、分隔线和间距表达层级。
5. **动作归属**：组级动作放在组尾，一个业务分组只保留一个保存动作。只要组内字段共享目标、权限和生命周期，就必须由一个批量接口原子提交；后端接口、数据表或历史提交方法不同不得制造多个保存。只有权限、风险、业务对象或生命周期确实独立时才可建立有标题的子区和独立动作，且按钮文案与反馈必须明确对应用户对象，不得暴露技术接口名。
6. **验收问题**：移除边框后仍应能仅靠标题、顺序和间距辨认各组；相邻组若可以用一个共同目标命名，就必须合并。桌面、移动端、只读、加载和空状态必须保持相同分组顺序。

后台页面结构评审必须列出“组名 → 用户目标 → 包含项 → 拆分理由”。新增或修改页面若未满足上述六条，不得以视觉偏好或已有代码为理由保留。

### 保存边界与草稿保护

- 一个业务分组的多个字段必须一次提交、一次成功反馈、一次失败回滚；禁止因已有多个单字段接口而显示多个“保存设置”，也禁止用连续多个请求伪装批量保存。
- 表单必须维护“服务端基线”和“当前草稿”的显式差异；无修改时保存动作禁用。提交期间用户继续输入时，成功回包只能确认已提交快照，不得把较新的本地草稿标记为已保存。
- 查询失效、窗口重新聚焦和后台刷新不得覆盖脏草稿；只有首次加载、业务对象切换或该分组无未保存修改时才可用远端数据重新水合。
- 草稿保护与保存并发规则分别处理：普通编辑沿用最后提交的整组内容为准，不因保护本地输入而新增版本冲突校验。已有版本校验的微博任务继续使用草稿首次水合时的版本，不能把后台刷新后的版本绑定到旧草稿；冲突时保留输入，由用户确认后重新加载。
- 查询到草稿的同步统一复用 `@lostsky/shared` 的 `useQueryDraft`，以团队、当前身份、业务对象和保存分组识别任务。共享字段与角色组件也维护自己的基线；props 刷新不能无条件重建输入或将父级标记为无修改。购买资料按字段 ID 保留已填写值，字段增删和校验规则变化只调整对应字段。
- 存在未保存修改时必须统一保护站内离开、刷新与关闭；浏览器卸载使用原生提示机制，不承诺所有环境都能阻止关闭或恢复草稿。同组件内更换业务对象也必须先保护草稿，不能在路由确认前重置表单；仅改变不影响任务身份的展示 query 时不应误报离开。取消后地址、目标与草稿保持不变。
- 同一应用出现两次即提取共享守卫；跨应用复用进入公共包，不得从另一个应用的源码目录导入，也不得在页面复制卸载与路由确认逻辑。页面声明脏状态和任务身份，共享层负责拦截与提示去重。
- 离开提醒与草稿恢复是两种能力。流程允许暂时进入辅助子任务再返回时，必须显式保留并恢复原草稿；保留成功后才可免除丢弃确认。普通离开仍需确认，不能用自动缓存代替用户对放弃修改的决定。
- 草稿按团队、当前身份、工作台范围、业务任务及目标对象隔离；新建任务也需区分独立实例，不能仅按完整 URL 或组件名共用。默认只保证当前应用会话内的辅助页面往返；刷新、关闭、跨标签页或跨应用恢复须另行约定，不默认将所有字段持久化到本地存储。
- 返回同一任务时恢复草稿，不由 query 或刷新结果覆盖。身份或团队切换后不得载入原上下文草稿，退出登录时清理；权限收回或目标失效时不得继续展示已受限数据，恢复与提交前重新核对访问范围。
- 保存成功只确认已提交快照，保留提交期间的新修改；显式放弃或任务完成后清理对应草稿。异步回包必须核对任务身份，不能覆盖后来切换的目标。页面层级、返回与 query 应用时机见[前端导航规范](../../architecture/frontend-navigation.md)。
- 批量接口必须验证全部字段后再写入，并在同一事务中记录审计；响应返回规范化后的完整分组状态，前端以此建立新基线。兼容性单字段接口可以保留，但新页面不得调用。

## 封闭组件契约

公共组件默认采用封闭视觉契约，执行“默认禁止、条件放行”，不得以“尽量复用”“尽量少传参数”等不可验收措辞代替。目标不是消灭所有参数，而是让调用方只表达业务差异，让视觉所有者独立保证一致性。

### 参数准入

- 公共参数只允许表达业务数据、真实状态、权限或禁用原因、用户可见语义、无障碍名称以及事件回调；例如值、`loading`、`disabledReason`、上传文件类型和按钮文案可以成为参数。
- 宽度、内外边距、圆角、阴影、控件排列、断点、移动端堆叠和内部图标间距属于视觉实现，默认不得下放为 `width`、`compact`、`layout`、`mobileStack` 等 props，也不得通过任意 class、style 或 CSS 变量入口变相暴露。
- 新参数只有在至少两个已经存在、业务意图相同且无法由组合或既有语义参数表达的真实变体需要时才可加入；必须先更新[公共组件契约](components.md)，再实现参数、迁移全部同义调用并覆盖默认值与所有真实变体。不得为单个页面、未来假设或规避修复组件默认行为而增加参数。
- 三个及以上调用方传递相同字面值或执行相同映射时，该值必须收回为组件默认值或语义组件内部规则，并删除重复下放；确有不同业务文案或约束时保留语义参数，不得为了减少参数把不同含义硬编码成同一内容。

### 调用方边界

- 页面和上层业务组件不得使用 `:deep(.ls-*)`、全局选择器、内联样式、任意 class 透传或 CSS 变量修改公共组件内部节点；不得依赖公共组件未登记的 DOM 层级和私有类名。
- 调用方只可设置组件根节点在外部布局中的轨道、顺序、对齐、可用宽度和组件间间距。需要改变组件内部控件尺寸或响应式时，必须回到视觉所有者修改默认契约，或按参数准入条件建立真实语义变体。
- 插槽用于承载契约明确允许的业务内容，不是绕过封闭契约的样式入口；插槽内容的外观由插槽契约和对应子组件负责。
- 第三方编辑器、浏览器原生文件输入等无法封闭的实现边界，必须在[公共组件](components.md)的“实现级例外”或[应用与页面](applications.md)具名登记，并进入精确源码白名单；例外必须说明影响范围、必要理由、失效条件和检查方法。

### 所有权判断

实施前必须依次回答：问题发生在组件内部还是组件之间；哪个组件是唯一视觉所有者；是否正在从父级穿透子级；新参数对应哪些已存在的真实变体；相同规则是否已经出现三次。无法明确视觉所有者时暂停编辑，先比较全部同义用法并收敛最小契约。

修复顺序固定为：修正视觉所有者默认契约 → 迁移全部同义用法 → 删除父级覆盖和重复参数 → 增加源码守卫 → 以结构化 DOM 尺寸验证结果。只在页面补一个 `:deep()`、只新增一个视觉 prop 或只让当前截图看起来正确，均不算完成。

## 抽象阈值

1. 已有同义组件时必须复用，禁止页面重写。
2. 同义结构出现三次及以上，必须在同一变更中抽象，并迁移全部同义实现。
3. 出现两次且包含状态、权限、移动端或无障碍逻辑，立即抽象并全量迁移。
4. 出现两次但只是简单布局时，记录为候选，暂不制造通用组件。
5. 单次、强业务语义结构保留在页面或应用内部组件，不进入公共 UI。

指标卡、金额分解、响应式表格的移动记录、分组权限编辑器和动态加入字段具有不同结构或业务意图，不因局部外观相似而合并。禁止为未来假设设计 props、万能 Schema 渲染器或只使用一次的公共组件；新参数必须对应已经存在的真实变体。

## 实施前组件化盘点

每次新增或修改后台页面结构前，Agent 必须先在 commentary 中简短列出：

- 已有可复用组件；
- 本次达到阈值的抽象候选；
- 仍应由页面承担的布局；
- 唯一视觉所有者、准备保留或新增的公共参数，以及是否存在父级穿透；
- 具名例外及理由。

固定流程为：搜索现有实现 → 比较业务意图 → 定义最小契约 → 创建组件 → 迁移全部同义用法 → 删除旧 CSS → 更新 Wiki、预览与测试。不得只替换新页面而保留旧的同义实现。

## 状态、适配与例外

公共组件必须覆盖其真实存在的加载、空、错误、禁用和权限状态；没有这些状态时不得虚构参数。组件内部负责 320px 起的自然换行、至少 44px 触控区、键盘与读屏语义；页面仍负责页面级无横向溢出和组件间布局。新增例外必须在[应用与页面](applications.md)具名登记理由、影响范围、失效条件和检查方法。

## 验收与自动守卫

- 公共组件必须在[后台公共组件](components.md)契约表和真实代码预览目录中可定位，并覆盖真实变体测试。
- 每次淘汰重复实现，必须同步增加“禁止旧实现”的源码契约，或维护精确允许清单；测试是 Wiki 规则的执行器，不能替代本页正文。
- 源码契约必须禁止页面和未登记组件出现 `:deep(.ls-*)`，并对公共组件参数表维护精确契约或等价 AST 检查；新增参数、视觉透传或私有类名依赖没有对应 Wiki 与白名单时必须使测试失败。
- 等宽、满宽、固定容器、换行和溢出等可观测布局要求必须使用 Playwright 或等价 DOM 测试读取计算样式与 `boundingBox()`；至少覆盖直接相关的桌面、移动端、长文案、禁用和加载状态。组件预览供人类验收，不能替代数值断言。
- 用户截图可由 Agent 直接读取，真实运行页可用于一次有界视觉验收；每个可见缺陷都必须先翻译成“哪些元素之间的哪种关系错误”，再对实际控件而非仅外层容器增加结构化回归。`frontend/component-previews/generated/*.png` 继续作为人类交付附件，不进入 Agent 输入。
- 搜索旧类名、直接基础控件和旧 CSS，确认全部同义实现已迁移；运行前端测试、类型检查、E2E、组件预览、文档构建和完整发布构建。
- 在 320、375、768、1024、1440px 与 200% 文本缩放下检查无横向溢出、标题层级、移动端按钮排列和触控区。
