# 参与开发

## 多模型代理分工

用户使用 GPT-6 Astra 主代理进行沟通、拆解、架构决策与最终验收；独立具体工作按下表委派。简单单点任务的实现可直接完成，Git 暂存与提交仍交 `lostsky-git`。

| 角色 | 模型 | 职责 |
| --- | --- | --- |
| `lostsky-explorer` | `gpt-6-luna` | 只读检索、调用链定位 |
| `lostsky-tester` | `gpt-6-luna` | 定向测试、复现与失败定位 |
| `lostsky-worker` | `gpt-6.1-sol` | 非前端代码实现与修复 |
| `lostsky-team-setting` | `gpt-6.1-sol` | TeamSetting 后端专项实现 |
| `lostsky-reviewer` | `gpt-6.1-sol` | 复杂逻辑、权限、事务审查 |
| `lostsky-frontend` | `gpt-6-astra` | 所有前端相关工作 |
| `lostsky-git` | `gpt-6-luna` | 阶段性暂存、任务提交、Git 生命周期检查与收尾，以及已授权的发布 |

模型由 `.codex/agents/*.toml` 的各角色配置固定指定；`lostsky-reviewer` 的推理强度固定为 `medium`，其他角色省略 `model_reasoning_effort`，由主代理按注册文件中的任务规则在创建时明确指定 `low` 或 `medium`。注释仅说明选择规则，不自动切换强度；未指定时按 Codex 的继承和默认规则解析。角色文件中的显式配置优先于创建参数。主对话模型由用户选择。修改角色配置后，在新任务中验证加载结果；已有代理继续使用创建时的配置。

- 前端优先按领域路由：所有前端相关检索、设计、实现、测试、审查和构建均由 Astra 主代理或 `lostsky-frontend` 执行，禁止交给 Luna / Sol。混合任务拆分前后端；不能合理拆分时整体交 Astra。此规则优先于角色和默认模型。所有非前端代码编写（含测试代码）交 Sol；Luna 除检索、执行测试与定位外，仅由 `lostsky-git` 执行 Git 暂存、提交与交付操作，不修改业务代码。
- 通常只开 1–2 个子代理，仅有独立且有价值的工作时并行，遵守运行时并发上限。
- 同一模块优先复用已有代理完成实现、修复和收尾，不重复创建职责相同的代理。审查聚焦最终差异和明确风险；只在新变化或失败证据需要时复审。
- 每次明确目标、文件或模块所有权、验收条件和必要上下文；告知代理共享工作区，不得回退他人改动。子代理不自行继续分派。
- 优先使用表中自定义角色。当前会话尚未加载角色时，使用通用角色并显式指定对应模型及按角色任务规则选择的推理强度；审查固定使用 `medium`。覆盖模型或推理强度时使用精简上下文或 `fork_turns="none"` 并提供完整子任务说明，不使用全量历史 fork。
- 主代理接受有证据的结果，避免重复检索、重跑已通过且无新变化的检查。Luna 遇到能力瓶颈升级 Sol，复杂跨模块问题交 Sol，关键决策与未解决问题交 Astra。
- 保留项目要求的验证；配置校验不等于模型调用成功。实际费用取决于账户计费，不保证固定节省比例。

配置格式参考 [Codex 子智能体官方文档](https://developers.openai.com/zh-Hans/docs/agent-configuration/subagents)。

## 开发流程

1. 阅读相关实现、测试、[项目文档](../index.md)和 OpenAPI。

4. 完成本地提交与适用的本地整合，说明变化、风险和验证结果；用户要求 PR 或远端交付时，再按相应授权处理。

## 任务拆分与自动分支

用户要求将分支管理纳入日常自动工作流。一次派发多个任务，或单个任务含可独立实施的步骤时，主代理先完成下列拆分，再调用项目技能 `.agents/skills/lostsky-task-orchestration/SKILL.md` 执行。Wiki 是规则正文，技能负责把规则连接到工具、代理和保全脚本。简单单点修改、只读问答不强制建立新环境。

### 选择隔离粒度

| 工作关系 | 默认方式 | 整合方式 |
| --- | --- | --- |
| 不同目标，可独立验收、交付或撤回 | 每个目标一个 `codex/<任务名>` 分支和独立 worktree | 分别验收，按依赖顺序合入目标分支 |
| 同一目标，步骤文件互斥且接口契约已确定 | 一个任务分支/worktree，按文件所有权分派子代理 | 一个 Git 负责人串行暂存、提交；整体验收 |
| 需要同时修改共享文件，或希望各步骤独立试验/审查 | 独立子分支/worktree，共同以已确认基线开始 | 在任务整合分支汇合后验收，不各自在 `main` 拼接半成品 |
| 下游依赖上游契约、schema、生成类型或公共组件 | 上游先完成并提交，后续基于该提交推进 | 依赖未稳定前只做独立检索或准备，不能假装独立并行 |
| 检索、审查或只读测试 | 指定被检查的绝对工作区与提交 | 通常不另建分支；会修改 fixture/共享数据库的测试须协调资源 |

隔离单位是可解释的交付，而不是每个文件、每条命令或每个代理。普通修复中的“定位→实现→测试”有天然依赖，不为三个阶段机械创建三个 worktree。多个独立用户目标不能因为文件暂时不冲突而混成一个无法拆分的提交。

### 启动与任务记录

1. 检查当前与目标工作区的分支、HEAD、暂存、未暂存、未跟踪文件及现有 worktree；区分当前任务与其他任务的归属。主工作区有其他任务写入时，自己的实现直接进入独立工作区，不先清理或暂存别人的文件。
2. 用简短 commentary 给出目标拆分、依赖及隔离选择。只对无法推断且影响正确性的范围询问；无需逐次询问是否创建分支或调用已授权的子代理。当前聊天的子任务使用子代理，除非用户明确要求，不创建新的用户聊天，也不向其他聊天发送指令。
3. 指定真实目标分支（默认 `main`）及其已核对的基线 SHA；优先复用确属本任务、未被占用的工作区，不复用已交付的其他任务分支。创建工作区时显式指定基线，不依赖工具的远端默认分支。优先使用应用提供的工作区创建/挂接工具；缺失时使用普通 `git worktree add` 并记录绝对路径。
4. 在 `git rev-parse --git-common-dir` 对应目录的 `codex/task-runs/<本次唯一标识>/` 保存不入库的任务记录，至少包括下表。每次阶段提交、基线更新、合并、保全、恢复和权限变化后更新；不把令牌、配置值或工作区原文放进公开报告。子代理领取任务前明确自己的绝对工作目录，所有命令使用该目录。

| 记录项 | 内容 |
| --- | --- |
| 任务 | 用户目标、验收条件、依赖任务及状态 |
| 所有权 | 负责代理、允许修改路径、共享文件唯一写入者 |
| Git | 仓库/任务/目标工作区、分支、基线 SHA、当前 HEAD、整合顺序 |
| 授权 | 本地提交/合并、push、部署、各类删除分别记录来源与限制 |
| 验证 | 命令、结果、日志路径、验证对应提交或 tree SHA、未验证边界 |
| 保全 | 快照位置、原 index/内容证据、新建 stash 的完整 SHA 和唯一标记、恢复与清理状态 |
| 资源 | 使用的端口、测试数据库/fixture、依赖目录、运行中进程及停止方式 |

状态可按“待开始→实施中→待验收→已验证→待整合→最终生命周期状态”推进。被阻塞的子任务保留原因，继续不依赖它的工作，不把其他目标标成完成。

### 委派与资源安排

- 遵循本页代理分工；通常仅同时运行 1–2 个实施代理。新建子代理时明确目标、目录、路径所有权、上游接口、成功条件和禁止覆盖其他改动。子代理不自行切分支、合并、清理环境或继续分派。
- 共用任务工作区时，OpenAPI、`package.json`、共享组件、字典源和 Changelog 均指定唯一写入者。代码生成由源文件负责人完成后通知执行者；不要多代理同时生成同一批类型或字典。需要交接同一文件时显式移交所有权。
- worktree 隔离源码，不隔离数据库、端口、缓存和外部服务。测试 fixture 使用独立标识与清理边界；共用数据库、同端口 E2E、全量类型检查和完整构建由主代理调度。内存不足时改串行，先停止本任务空闲服务，不重启或停止他人服务。
- 锁文件未变化且依赖可安全复用时避免反复安装；有指向原源码的 workspace 包、可变缓存或生成输出时不得盲目链接依赖目录。不得将 `.env`、缓存、日志、快照、临时数据库或可再生产物提交。

### 自动推进与整合门禁

本项目的日常默认授权包括：为用户已派发的范围创建隔离分支/worktree、委派、定向验证、阶段暂存、本地提交，以及验收通过后的普通本地合并。目标未指定时为 `main`。该授权源于用户对自动分支工作流的要求，只适用于当前任务，不能代替其他任务的提交授权；用户要求“仅审查”“先不要合并”或指定目标时优先遵守。push、部署、远端写操作和分支/worktree 删除不包含在此默认授权中。

由 `lostsky-git` 串行整合，每次只操作一个目标工作区：

1. 先冻结准备交付的源码，完成定向检查；前端按约定执行完整静态构建。记录被验证的 tree SHA 或提交 SHA。构建中继续改代码会使相关结果失效，应修复后再启动最终构建，不并行启动多次同名构建。
2. 再核对目标 HEAD 与任务基线。目标已前进时，在任务/整合工作区普通合并最新目标，不在有其他工作进行的主工作区直接解冲突。依赖链按上游到下游整合；多个独立分支逐个整合，每次使用新的目标 HEAD。
3. Git 代理负责报告冲突和保留现场；主代理把业务冲突交给对应领域代理，保留双方意图并针对差异验收。已授权任务中的机械冲突可直接修复，无需再次请求合并许可。需求相互矛盾或归属无法确定时才询问；禁止整文件选 ours/theirs、自动 abort 或改写历史来绕过冲突。
4. 生成文件从合并后的源重生。原来的注册列表、目录契约和计数随实际内容同步，不为通过测试降低门禁。只有生成器语义内容有变化时纳入提交；仅 stat/EOL 残留经确认后对精确路径 `git add` 刷新，再确认没有新暂存差异，不用恢复命令覆盖文件。
5. 按源码与共享契约的实际变化复验。相同 tree、相同测试相关环境的已通过结果直接复用；文档或测试报告移动不触发重复业务测试。提交/快进后证明 tree 与已验证 tree 相同即可对齐证据，不因 SHA 不同重复完整构建。数据库、配置或依赖发生变化则重新判断受影响检查。
6. 更新目标前再次核对 HEAD、index、脏文件及活动写入者。若目标变化，回到整合步骤；目标有无关改动则按下节保全，不能覆盖或顺手提交。目标干净且基线吻合时，以 `--ff-only` 推进到已验收的整合提交；失败就重新检查关系，不 force。
7. 恢复所有保全内容与原暂存边界，核对任务提交在目标历史中；单独报告目标原有未提交内容。完成后进入下文生命周期状态。默认保留本地任务分支/worktree，已获得清理授权时才做清理；不以本地合并代称推送或部署。

### 精确保全与恢复

临时保全只在目标没有活动写入且归属、恢复方式明确时使用；若其他聊天或代理仍在写入，不因一次状态读取显示空闲就假定其所有子代理已停，先核对各写入者或等待其结束。不得擅自中断、给其他聊天发消息或移动它们的工作。

- 操作前保存 staged/unstaged 的二进制补丁、index 语义、所有待保全 tracked/untracked 文件的原始字节副本和 SHA-256、删除及重命名信息、HEAD 与状态；仅有补丁或 SHA 不足以重建混合换行和二进制原文件。可使用技能的 `scripts/worktree_snapshot.py` 创建和核对只读快照；快照目录不进入任何工作区，不收集 ignored 秘密配置。
- 先完成首尾一致性检查，再按精确路径保全。已有暂存内容必须保留其 staged/unstaged 边界；无法可靠恢复时不 stash。创建 stash 后立即记录完整对象 SHA 和唯一标记，核对新对象确实包含预期路径；不把可变化的 `stash@{0}` 当身份。共享 stash 栈发生并发变动时停止猜测。
- 恢复优先 apply 已记录 SHA 并保留备份，不使用 pop 把恢复和删除绑在一起。恢复前后都检查是否有新的并发写入。未被合并改变的原文件恢复原字节并核对 SHA；被合并改变的文件须逐项证明原改动和新合并内容都保留，不能用旧整文件覆盖新功能。
- 保留原 index 语义与未跟踪状态，逐项核对删除、重命名、二进制和换行。快照校验失败只报告差异，不能当成覆盖文件的许可；单纯 EOL 差异也先在临时副本验证预期 SHA，再决定恢复。
- 内容与暂存状态完整恢复后，根据已记录的 stash SHA 重新定位 selector，仅删除本次已恢复的临时 stash。SHA/归属证据不足就保留并报告。外部快照、尚需保留的测试证据及 ignored 文件明确登记，不以“Git clean”宣称它们已清理。

## 工作区保护与阶段性暂存

暂存区用于保存“当前任务中已经确认的基线”，帮助区分已验证结果与后续修改；它不是备份、提交或完成标志，也不能阻止文件再次被覆盖。长期保留或交接仍应使用正常提交。主代理负责确定已验证切片和文件归属，并在达到阶段性暂存或可提交状态时主动调用 `lostsky-git`；该子代理核对范围后主动执行暂存与适用的本地提交，无需用户另行要求。

1. 开始任务时先运行 `git status --short` 和 `git diff --cached --name-only`，识别工作区与暂存区中已有内容；已有差异默认属于用户或其他任务，不得顺手纳入、回退或清空。
2. 只有一个切片能够独立说明、已完成直接相关验证且准备继续进行后续工作时，才建立暂存基线。长任务、上下文切换、委派、用户确认结果，以及执行可能覆盖文件的生成、恢复或批量修改前，应优先考虑暂存；尚未验证的试验代码和半成品不暂存。
3. 使用 `git add -- <明确路径>` 暂存完全归属当前切片的文件；禁止使用 `git add .`、`git add -A` 或宽泛目录把无关差异一起纳入。同一文件混有其他任务差异时，只能在确认每个区块归属后使用 `git add -p -- <路径>` 逐块暂存；不能可靠拆分时保持未暂存并先解决边界。
4. 暂存后立即运行 `git diff --cached --name-only` 和 `git diff --cached --check`，再审查 `git diff --cached -- <路径>`，确认暂存内容完整、可解释且没有凭据、生成物或无关变化。继续修改后，`git diff` 表示相对暂存基线产生的新工作区差异，`git diff --cached` 表示已确认基线。
5. 不得用 `git reset`、`git restore --staged`、`git checkout` 或等价操作清空、重建或覆盖已有暂存内容，除非用户明确授权且目标已逐项核对。发现暂存区已有无关内容时保留原状，只追加能够明确归属的区块。
6. 提交、发布或交接前重新审查暂存区；测试范围仍按当前任务实际修改的契约判定，不因文件已暂存而扩大，也不把暂存成功当作验证通过。

禁止提交凭据、Token、Cookie、个人路径和内部地址。确认但暂不处理的工作写入[待办](../TODO.md)。

## Git 任务生命周期

主代理负责跟踪每个独立分支、worktree、临时开发环境和并行 Codex 任务，开发代理不自行删除工作环境。阶段性暂存、任务提交以及任务结束时的状态检查与收尾交给 `lostsky-git`，并将生命周期归入以下一种明确状态：

- 已合并并清理；
- 已合并但保留环境；
- 已完成但等待审查；
- 因异常保留现场；
- 明确决定不合并。

用户要求完成的任务及其明确范围内、经验证的改动，可以由 `lostsky-git` 正常提交并按[自动推进与整合门禁](#task-orchestration)完成普通本地合并；其他任务的已有暂存内容和归属不明的改动不因此获得提交授权。push、部署、worktree 删除和分支删除仍须独立授权；会话中已有且仍适用于当前目标的授权可以沿用。用户未另行指定目标分支时，默认合入 `main`；用户明确要求等待审查或不合并时优先遵守。

### 调用时机

以下情况主代理主动调用 `lostsky-git`，不得等用户再次提醒暂存或提交：

- 当前任务的独立切片已完成直接验证，需要建立暂存基线；
- 当前任务的改动经验证且达到可提交状态，即使未使用独立分支或 worktree；`lostsky-git` 核对归属后直接暂存并提交；
- 开发代理已完成实现，修改已提交或已达到可提交状态，必要测试、lint、build 等验证已有结果，并且任务使用独立分支或 worktree；
- 用户要求合并、收尾、清理或结束任务；
- 使用独立 worktree 或任务分支的并行任务结束；
- 发布完成后仍有临时 release、preview 分支或 worktree；
- 发现疑似遗留的已合并任务分支、已结束 worktree、detached/stale worktree，或远端已删除但本地仍存在的任务分支。

“代码写完”本身不表示可以删除环境。存在未提交修改或未跟踪文件时，代理先逐项核对归属、内容与验证状态：能确认属于当前任务的，完成验证并按明确路径或区块提交；能确认属于其他已完成任务且有适用授权的，独立验收、独立提交；可安全临时保全的文件，在记录原位置与校验信息后保全并于操作后恢复。不能确认归属或安全恢复方式、验证失败、存在冲突或活动任务占用时，保留现场并报告具体阻碍，不要求用户先手工清空工作区。仍需人工审查、用户指定的目标存在歧义或可能有重要未推送提交时，只执行已获授权且安全的步骤。

| 删除任务 worktree | 保留 | 明确允许删除，且任务提交已安全保留、worktree 无任何未提交内容 |
| 删除本地任务分支 | 保留 | 明确允许删除，且可证明任务提交已安全保留 |

### 检查与执行

代理先确认传入的仓库和 worktree 都是解析后的绝对路径，并验证 worktree 实际属于该仓库、确属本任务且不是当前工作区或主工作区。至少检查：

- 任务 worktree 与目标分支所在 worktree 的 `git status`、当前分支、HEAD SHA、worktree 列表，以及未提交、未跟踪和忽略文件；合并前二者都必须干净，删除前不能只依据 tracked 文件状态；
- 任务分支、目标分支、本地与远端 tip、merge-base 和提交关系；
- 未推送提交、冲突或进行中的 Git 操作；
- 相关分支是否被其他 worktree、代理或活动任务占用，目标工作区是否有其他任务并行写入；
- 已有验证是否确实对应准备合并的 commit SHA。

发现脏工作区时，先按上述归属与验证流程处理。不得为了收尾把未验证或归属不明的改动混入任务提交，也不得丢弃、静默隐藏或删除；临时保全必须可核验、可恢复，结束前核对原位置和内容。无法安全处理的具体项目保留现场并报告，其余独立步骤继续执行。禁止 `reset --hard`、`clean`、force push、`branch -D`、`worktree remove --force` 以及改写历史。

本地任务整合以已核对的本地目标 HEAD 为基线，不强制 fetch 或声称与远端同步。涉及远端更新或推送时先核对远端；从远端更新本地目标只能安全 fast-forward，不能覆盖本地分叉历史。合并冲突由主代理按上文派发领域修复，Git 代理不自行处理业务语义或 abort。整合结果按影响范围验证并记录其 SHA；前端相关验证必须交 Astra 主代理或 `lostsky-frontend`。要求 push 时，必须在 push 成功并核对远端目标已指向预期提交后才能清理。

未推送提交默认保留。只有“允许仅在本地目标分支保留结果后清理”有明确用户授权，且目标分支已包含任务提交，才可在未推送时继续清理。普通 merge 可以用包含关系证明提交已保留；squash、rebase 或 cherry-pick 后仅做祖先检查不足以证明等价，证据不足时不得自动删除分支或 worktree。

清理必须按顺序执行：先确认任务结果安全存在于目标分支，再确认 worktree 包括未跟踪和忽略文件在内均无待保留内容，然后删除任务 worktree，最后按各自授权删除本地、远端任务分支。不得删除当前工作区或主工作区。只处理已确认属于本任务的失效 worktree 元数据；不得顺手全局 prune 其他遗留项。远端分支删除前重新读取远端 tip，发现变化即停止。
