# 参与开发

## 多模型代理分工

用户使用 GPT-6 Astra 主代理进行沟通、拆解、架构决策与最终验收；独立具体工作按下表委派。简单单点任务的实现可直接完成，Git 暂存与提交仍交 `lostsky-git`。

| 角色 | 模型 | 职责 |
| --- | --- | --- |
| `lostsky-explorer` | `gpt-6-luna` | 只读检索、调用链定位 |
| `lostsky-tester` | `gpt-6-luna` | 定向测试、复现与失败定位 |
| `lostsky-worker` | `gpt-6.1-sol` | 非前端代码实现与修复 |
| `lostsky-team-setting` | `gpt-6.1-sol` | TeamSetting 后端专项实现 |
| `lostsky-reviewer` | `gpt-6.1-sol` | 复杂逻辑、权限、事务审查 |
| `lostsky-frontend` | `gpt-6-astra` | 所有前端相关工作 |
| `lostsky-git` | `gpt-6-luna` | 阶段性暂存、任务提交、Git 生命周期检查与收尾，以及已授权的发布 |

模型与推理强度由 `.codex/agents/*.toml` 的各角色配置明确指定，默认使用 `medium`；主对话模型由用户选择。修改角色配置后，在新任务中验证加载结果；已有代理继续使用创建时的配置。

- 前端优先按领域路由：所有前端相关检索、设计、实现、测试、审查和构建均由 Astra 主代理或 `lostsky-frontend` 执行，禁止交给 Luna / Sol。混合任务拆分前后端；不能合理拆分时整体交 Astra。此规则优先于角色和默认模型。所有非前端代码编写（含测试代码）交 Sol；Luna 除检索、执行测试与定位外，仅由 `lostsky-git` 执行 Git 暂存、提交与交付操作，不修改业务代码。
- 通常只开 1–2 个子代理，仅有独立且有价值的工作时并行，遵守运行时并发上限。
- 同一模块优先复用已有代理完成实现、修复和收尾，不重复创建职责相同的代理。审查聚焦最终差异和明确风险；只在新变化或失败证据需要时复审。
- 每次明确目标、文件或模块所有权、验收条件和必要上下文；告知代理共享工作区，不得回退他人改动。子代理不自行继续分派。
- 优先使用表中自定义角色。当前会话尚未加载角色时，使用通用角色并显式指定对应模型及 medium 推理强度；覆盖模型时使用精简上下文或 `fork_turns="none"` 并提供完整子任务说明，不使用全量历史 fork。
- 主代理接受有证据的结果，避免重复检索、重跑已通过且无新变化的检查。Luna 遇到能力瓶颈升级 Sol，复杂跨模块问题交 Sol，关键决策与未解决问题交 Astra。
- 保留项目要求的验证；配置校验不等于模型调用成功。实际费用取决于账户计费，不保证固定节省比例。

配置格式参考 [Codex 子智能体官方文档](https://developers.openai.com/zh-Hans/docs/agent-configuration/subagents)。

## 开发流程

1. 阅读相关实现、测试、[项目文档](../index.md)和 OpenAPI。
2. 只修改本次目标涉及的内容，同步代码、契约、数据库、测试和文档。
3. 按[测试须知](testing.md)验证，只报告实际结果。
4. 提交合并请求，说明变化、风险和验证结果。

详见：[开发须知](development.md) · [代码更新清单](checklist.md) · [测试须知](testing.md) · [发布须知](releasing.md)

## 工作区保护与阶段性暂存

暂存区用于保存“当前任务中已经确认的基线”，帮助区分已验证结果与后续修改；它不是备份、提交或完成标志，也不能阻止文件再次被覆盖。长期保留或交接仍应使用正常提交。主代理负责确定已验证切片和文件归属，并在达到阶段性暂存或可提交状态时主动调用 `lostsky-git`；该子代理核对范围后主动执行暂存与适用的本地提交，无需用户另行要求。

1. 开始任务时先运行 `git status --short` 和 `git diff --cached --name-only`，识别工作区与暂存区中已有内容；已有差异默认属于用户或其他任务，不得顺手纳入、回退或清空。
2. 只有一个切片能够独立说明、已完成直接相关验证且准备继续进行后续工作时，才建立暂存基线。长任务、上下文切换、委派、用户确认结果，以及执行可能覆盖文件的生成、恢复或批量修改前，应优先考虑暂存；尚未验证的试验代码和半成品不暂存。
3. 使用 `git add -- <明确路径>` 暂存完全归属当前切片的文件；禁止使用 `git add .`、`git add -A` 或宽泛目录把无关差异一起纳入。同一文件混有其他任务差异时，只能在确认每个区块归属后使用 `git add -p -- <路径>` 逐块暂存；不能可靠拆分时保持未暂存并先解决边界。
4. 暂存后立即运行 `git diff --cached --name-only` 和 `git diff --cached --check`，再审查 `git diff --cached -- <路径>`，确认暂存内容完整、可解释且没有凭据、生成物或无关变化。继续修改后，`git diff` 表示相对暂存基线产生的新工作区差异，`git diff --cached` 表示已确认基线。
5. 不得用 `git reset`、`git restore --staged`、`git checkout` 或等价操作清空、重建或覆盖已有暂存内容，除非用户明确授权且目标已逐项核对。发现暂存区已有无关内容时保留原状，只追加能够明确归属的区块。
6. 提交、发布或交接前重新审查暂存区；测试范围仍按当前任务实际修改的契约判定，不因文件已暂存而扩大，也不把暂存成功当作验证通过。

禁止提交凭据、Token、Cookie、个人路径和内部地址。确认但暂不处理的工作写入[待办](../TODO.md)。

## Git 任务生命周期

主代理负责跟踪每个独立分支、worktree、临时开发环境和并行 Codex 任务，开发代理不自行删除工作环境。阶段性暂存、任务提交以及任务结束时的状态检查与收尾交给 `lostsky-git`，并将生命周期归入以下一种明确状态：

- 已合并并清理；
- 已合并但保留环境；
- 已完成但等待审查；
- 因异常保留现场；
- 明确决定不合并。

用户要求完成的任务及其明确范围内、经验证的改动，可以由 `lostsky-git` 正常提交；其他任务的已有暂存内容和归属不明的改动不因此获得提交授权。安装本规则不授权 merge、push、worktree 删除或分支删除；会话中已有且仍适用于当前目标的用户授权可以沿用。用户未另行指定目标分支时，默认合入 `main`；用户明确指定其他分支时以其为准。默认目标不构成 merge 授权，仍须满足全部安全验收要求。

### 调用时机

以下情况主代理主动调用 `lostsky-git`，不得等用户再次提醒暂存或提交：

- 当前任务的独立切片已完成直接验证，需要建立暂存基线；
- 当前任务的改动经验证且达到可提交状态，即使未使用独立分支或 worktree；`lostsky-git` 核对归属后直接暂存并提交；
- 开发代理已完成实现，修改已提交或已达到可提交状态，必要测试、lint、build 等验证已有结果，并且任务使用独立分支或 worktree；
- 用户要求合并、收尾、清理或结束任务；
- 使用独立 worktree 或任务分支的并行任务结束；
- 发布完成后仍有临时 release、preview 分支或 worktree；
- 发现疑似遗留的已合并任务分支、已结束 worktree、detached/stale worktree，或远端已删除但本地仍存在的任务分支。

“代码写完”本身不表示可以删除环境。存在未提交修改或未跟踪文件时，代理先逐项核对归属、内容与验证状态：能确认属于当前任务的，完成验证并按明确路径或区块提交；能确认属于其他已完成任务且有适用授权的，独立验收、独立提交；可安全临时保全的文件，在记录原位置与校验信息后保全并于操作后恢复。不能确认归属或安全恢复方式、验证失败、存在冲突或活动任务占用时，保留现场并报告具体阻碍，不要求用户先手工清空工作区。仍需人工审查、用户指定的目标存在歧义或可能有重要未推送提交时，只执行已获授权且安全的步骤。

### 权限与任务提示

主代理调用时应填写下列信息；目标分支未另行指定时填写 `main`，其他未知项写“未知，检查确认”，不得猜测：

```text
你是本项目的 Git 交付与生命周期代理。主动处理当前任务已验证改动的暂存与可提交改动的本地提交，并统一处理收尾，严格执行
docs/dev/development/contributing.md#git-task-lifecycle。

任务：{{TASK_DESCRIPTION}}
仓库绝对路径：{{REPOSITORY_PATH}}
任务分支：{{TASK_BRANCH}}
目标分支：{{TARGET_BRANCH，未另行指定时为 main}}
任务 worktree 绝对路径：{{WORKTREE_PATH}}
验证状态（命令、结果、对应 commit SHA）：{{VALIDATION_STATUS}}
是否需要人工审查：{{REVIEW_REQUIRED}}
已知异常或限制：{{KNOWN_ISSUES}}
授权来源（当前用户消息或可沿用的会话授权）：{{AUTHORIZATION_SOURCE}}

允许提交的任务范围与提交说明：{{COMMIT_SCOPE}}
允许自动合并：{{ALLOW_MERGE}}
允许删除任务 worktree：{{ALLOW_WORKTREE_DELETE}}
允许删除本地任务分支：{{ALLOW_LOCAL_BRANCH_DELETE}}
允许删除远端任务分支：{{ALLOW_REMOTE_BRANCH_DELETE}}
允许 push：{{ALLOW_PUSH}}
要求 push：{{REQUIRE_PUSH}}
允许仅在本地目标分支保留结果后清理：{{ALLOW_LOCAL_ONLY_RETENTION}}

先核对实际状态，主动处理可确认归属的工作区改动并完成适用验收。
权限未知或条件不满足时，仅停止对应操作，继续完成独立且安全的步骤。
```

各操作独立授权，不能用一项授权代替另一项：

| 操作 | 默认边界 | 执行条件 |
| --- | --- | --- |
| commit | 仅提交当前任务范围内经验证的改动 | `lostsky-git` 核对路径或区块、已有暂存内容和验证结果后提交；其他任务改动须有适用授权 |
| merge | 默认目标为 `main`，只报告提交关系 | 目标已按用户指定或默认值确定、允许合并、验证有效且没有冲突或工作丢失风险 |
| push | 不推送 | 明确允许 push、远端与 refspec 已核对；是否为清理前置条件由“要求 push”单独决定 |
| 删除任务 worktree | 保留 | 明确允许删除，且任务提交已安全保留、worktree 无任何未提交内容 |
| 删除本地任务分支 | 保留 | 明确允许删除，且可证明任务提交已安全保留 |
| 删除远端任务分支 | 保留 | 明确允许删除，并在执行前重新核对远端 tip 没有并发新增提交 |

### 检查与执行

代理先确认传入的仓库和 worktree 都是解析后的绝对路径，并验证 worktree 实际属于该仓库、确属本任务且不是当前工作区或主工作区。至少检查：

- 任务 worktree 与目标分支所在 worktree 的 `git status`、当前分支、HEAD SHA、worktree 列表，以及未提交、未跟踪和忽略文件；合并前二者都必须干净，删除前不能只依据 tracked 文件状态；
- 任务分支、目标分支、本地与远端 tip、merge-base 和提交关系；
- 未推送提交、冲突或进行中的 Git 操作；
- 相关分支是否被其他 worktree、代理或活动任务占用，目标工作区是否有其他任务并行写入；
- 已有验证是否确实对应准备合并的 commit SHA。

发现脏工作区时，先按上述归属与验证流程处理。不得为了收尾把未验证或归属不明的改动混入任务提交，也不得丢弃、静默隐藏或删除；临时保全必须可核验、可恢复，结束前核对原位置和内容。无法安全处理的具体项目保留现场并报告，其余独立步骤继续执行。禁止 `reset --hard`、`clean`、force push、`branch -D`、`worktree remove --force` 以及改写历史。

允许自动合并时，目标分支只能从已确认的远端状态安全 fast-forward 更新；无法 fast-forward 时停止。合并发生冲突时保留冲突现场并报告，不擅自继续或 abort。合并后按影响范围重新验证合并结果并记录其 SHA；前端相关验证必须交 Astra 主代理或 `lostsky-frontend`。要求 push 时，必须在 push 成功并核对远端目标已指向预期提交后才能清理。

未推送提交默认保留。只有“允许仅在本地目标分支保留结果后清理”有明确用户授权，且目标分支已包含任务提交，才可在未推送时继续清理。普通 merge 可以用包含关系证明提交已保留；squash、rebase 或 cherry-pick 后仅做祖先检查不足以证明等价，证据不足时不得自动删除分支或 worktree。

清理必须按顺序执行：先确认任务结果安全存在于目标分支，再确认 worktree 包括未跟踪和忽略文件在内均无待保留内容，然后删除任务 worktree，最后按各自授权删除本地、远端任务分支。不得删除当前工作区或主工作区。只处理已确认属于本任务的失效 worktree 元数据；不得顺手全局 prune 其他遗留项。远端分支删除前重新读取远端 tip，发现变化即停止。

- 合并状态：
- Push 状态：
- Worktree 状态：
- 本地任务分支状态：
- 远端任务分支状态：
- 最终验证及对应 SHA：
- 生命周期最终状态：
