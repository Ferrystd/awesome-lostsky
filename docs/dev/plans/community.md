# Community 应用计划

> 状态：未实现。本页描述待开发能力，不代表当前版本已经提供。

## 目标与应用边界

新增类似微博超话的社区应用：用户围绕一个主题加入社区、浏览板块、发帖和讨论。平台拥有官方社区，用于公告、更新、反馈与平台用户沟通；团队可创建和管理自己的社区，并分配社区管理员。

Community 是 **teamless 应用**，统一入口拟为 `community.lostsky.work`，API 支持 `community.api.lostsky.work`。网址中的社区 slug 只定位社区，不决定操作者身份或要求操作者属于社区所有者团队。

登录与身份沿用 Account：发帖、评论、加入和社区日常管理使用当前有效 Entity；Community 显示只读身份及前往 Account 切换身份的入口。公开社区和公开内容允许访客浏览，写入要求登录和有效 Entity。真实 user 用于认证与审计，不作为隐式业务身份。

## 所有权与管理入口

社区有两种所有权，分别是平台和团队。平台社区没有所属团队，团队社区必须关联一个团队；官方标记仅用于平台社区，不允许团队自行声明。首版不提供社区所有权转移。

| 入口 | 管理对象 | 授权依据 | 首版职责 |
| --- | --- | --- | --- |
| Community | 当前社区 | 当前 Entity 的社区管理员关系 | 板块、公告、帖子、评论与社区成员的日常管理 |
| Team | 当前团队拥有的社区 | 目标团队的社区管理 Permission | 创建社区、维护资料和状态、分配或移除社区管理员，跳转日常管理 |
| Admin | 平台拥有的社区，包括官方社区 | 平台社区 Permission | 创建平台社区、维护资料和状态、分配或移除社区管理员，管理板块、公告、内容与成员 |

团队管理者不必加入社区即可在 Team 管理所属社区。Admin 的平台社区管理者不必领取 Entity 或加入社区即可执行平台管理操作，沿用 Admin 的 user 认证与平台审计。

**社区管理员绑定全局 Entity。** Team 和 Admin 都可通过准确 Entity slug 分配有效 Entity，不要求它归属于某个团队。社区管理员在 Community 行使管理权，无需获得 Team 或 Admin 的后台访问资格。为平台社区增加管理员不会把该账号变成平台管理员，也不会授予其他平台资源权限。

Team 社区管理 Permission 只覆盖目标团队拥有的社区；Admin 的社区管理 Permission 只覆盖平台拥有的社区。首版不引入 Admin 代管团队社区或编辑团队社区内容的能力。

## 首版用户流程

1. 访客进入社区广场，浏览公开社区、简介、板块和帖子；登录后查看“我加入的社区”。
2. 当前 Entity 加入公开社区后可以发帖、评论和点赞，退出后保留已有内容与作者关联。首版社区统一公开、自由加入，不引入私密社区和加入审批。
3. 社区首页展示名称、简介、所有者、官方标记、加入状态、置顶公告与帖子流；按板块筛选，首版按发布时间倒序，不引入推荐算法。
4. 发帖选择一个板块，填写标题和正文；帖子详情提供评论、点赞、作者与发布时间。首版使用现有 Markdown 能力，不新增独立媒体上传体系或转发机制。
5. 作者可编辑和删除自己的帖子、评论；社区管理者可置顶、取消置顶、隐藏或恢复内容，不能冒用作者改写正文。作者删除后展示删除状态，管理员隐藏后从普通列表移除，并向作者显示处理原因。
6. 社区管理员在 Community 管理板块、公告和内容，禁言或解除禁言某个 Entity。禁言只限制该社区的发帖与评论，不封禁平台账号，也不影响其他社区。

首版不提供聊天、积分、签到、等级、推荐算法、多层评论、举报工单或复杂审批。平台与用户的沟通由官方社区公告和普通帖子讨论承载。

## Admin 平台社区管理

Admin 侧栏增加“平台社区”，列表只展示平台拥有的社区，可按名称和状态筛选。详情按实际任务提供以下管理区：

- **资料与状态**：创建平台社区，维护名称、slug、简介、官方标记；暂停或恢复社区。暂停时仍可浏览已有公开内容，不能加入、发帖、评论或点赞，管理者仍可处理内容。首版不提供物理删除社区。
- **管理员**：展示管理员 Entity 与当前有效状态，通过准确 slug 添加、移除管理员；允许平台管理者在社区暂无管理员时重新分配。社区管理员不能在 Community 自行任命管理员或扩大权限。
- **板块与公告**：新增、编辑、排序、停用板块；发布和取消置顶公告。停用板块不删除已有帖子，禁止再向该板块发新帖；恢复后继续使用。
- **内容**：查询帖子和评论，置顶帖子、隐藏或恢复帖子及评论。帖子置顶与公告分开表达，隐藏帖子时其评论一并不可公开访问。
- **成员**：查看已加入 Entity，禁言、解除禁言；禁言关系独立于加入关系，退出再加入不会解除禁言。

平台社区读取、资料/状态与管理员维护、内容日常治理分别拟使用 `admin.community.read`、`admin.community.write`、`admin.community.moderate`。管理页面需要读取权限，两个写权限互不替代：`write` 不自动获得内容治理权，`moderate` 不允许任命管理员。现有 `super_admin` 按平台机制拥有这些权限。

Admin 写操作记录真实操作者、社区、动作与结果；隐藏内容、禁言和暂停社区要求填写原因。管理动作复用集中业务审计，平台事件不伪造 Entity 或团队归属。此处是对 Admin 当前业务范围的计划扩展，实现时再同步应用正文和权限字典。

## Team 与 Community 管理

Team 增加“团队社区”入口，只列出地址团队拥有的社区。拟使用 `community.team.read` 和 `community.team.manage`，沿用 `TeamWorkspaceAuth` 与目标团队 Permission；具备管理权限的外部 Entity 也可管理目标团队社区，不因此改变自身身份。

Team 负责创建、资料和状态维护、管理员任命，并可通过所属团队管理权处理社区日常内容；Community 负责阅读、互动和日常管理。Team 的日常管理链接跳转 Community，服务端继续按该社区的所有者团队校验管理权限，不能仅靠前端入口授权。团队状态不可用时禁止新增社区及互动写入，已有公开内容保留读取。

Community 中，社区管理员可以管理板块、公告、内容和禁言；团队所有者的管理权可按目标团队 Permission 校验，不依赖其是否已被单独列为社区管理员。平台后台权限不直接转成 Community 的 Entity 管理权；平台管理者使用 Admin，或显式分配一个 Entity 为社区管理员后使用 Community。

## 数据与接口设计

实施时按现有模型规范确认命名，首版只建立必要关系：

| 对象 | 关键关系与状态 |
| --- | --- |
| 社区 | 全局唯一 slug、所有权类型、团队 ID（平台为空）、资料、官方标记、正常/暂停 |
| 板块 | 所属社区、名称、排序、启用/停用；新社区创建默认讨论板块 |
| 加入关系 | 社区与 Entity 唯一组合、加入时间；退出移除加入关系 |
| 管理员关系 | 社区与 Entity 唯一组合；独立于加入关系 |
| 禁言关系 | 社区与 Entity 唯一组合、原因；解除时移除限制 |
| 帖子 | 所属社区与板块、作者 Entity、标题、正文、置顶、作者删除/管理隐藏状态 |
| 评论 | 所属帖子、作者 Entity、正文、作者删除/管理隐藏状态；首版单层 |
| 点赞关系 | 帖子与 Entity 唯一组合；评论点赞不纳入首版 |

作者、成员和管理员外键统一引用 `entity.id`，不重复存储成员类型或团队成员子表 ID。平台创建和治理通过审计记录 user，不为平台伪造业务 Entity。

Community API 提供广场、社区详情、板块、帖子和评论读取，以及当前 Entity 的加入、退出、发帖、编辑、删除、评论、点赞和日常管理。Team 与 Admin 各自提供所属范围的列表、创建、资料/状态、管理员维护与治理接口，复用同一社区服务，分别校验其授权来源。

板块、帖子、评论、管理员和成员查询均从目标社区收口；不能仅验证资源 ID 存在。社区管理权不授予修改其他社区、平台账号或团队角色的权限。成员禁言不影响社区管理权限，需要停止其管理时应明确移除管理员关系。

采用现有请求去重、数据库唯一约束、事务与 Markdown 清洗，不另外增加权限缓存、重试框架、通用工作流或预留复杂角色体系。多表写入只围绕实际一致性需求使用事务。

## 实施顺序

1. **基础与契约**：建立 Community teamless 应用解析、模型与表；明确上述权限，补齐 Community、Team、Admin OpenAPI 和集中审计。
2. **后台管理**：先完成 Team 团队社区与 Admin 平台社区的创建、资料、状态和管理员分配，使社区具备明确所有者和可用管理入口。
3. **社区互动**：实现广场、社区首页、板块、帖子详情、加入、发帖、评论和点赞，以及只读身份和 Account 跳转。
4. **治理与交付**：完成三处授权来源对应的日常治理、状态展示、定向测试与前端完整静态构建，更新应用与架构正文。人工用户文档由维护者补充，不自动改写。

页面实施前按后台组件化方法盘点公共布局与重复用法，使用现有后台组件和 Markdown 编辑器；本计划不提前创建占位页面、权限或组件。

## 验收条件

- 统一域名可以浏览不同团队和平台的社区；更换社区 slug 不切换人员身份，也不要求加入所有者团队。
- 平台可通过 Admin 创建官方社区、任命跨团队 Entity 管理员，并完成板块、公告、帖子、评论、成员禁言和社区暂停管理。
- 被任命者在 Community 获得指定社区的管理入口与能力，但没有 Admin 平台访问资格；移除或 Entity 失效后下一次管理请求拒绝。
- Team 只能维护目标团队的社区，Admin 平台社区管理只能维护平台社区；替换社区或下级资源 ID 不能越权。
- Admin 的读、资料/管理员写、内容治理权限分别验证；普通社区管理员不能分配管理员或修改所有权。
- 访客只能读取公开内容；未加入、被禁言、社区暂停或板块停用时，按对应范围拒绝互动写入，保留可解释状态。
- 隐藏帖子后详情、评论与列表均不泄露隐藏正文；作者删除、成员退出、管理员移除不抹去其他业务历史。
- 重复加入和点赞不产生重复关系；主体始终取当前 Entity，身份切换后旧页面不能误用新身份提交。
- 管理动作审计能区分 Admin user 与 Community/Team Entity，包含正确社区与处理原因。
- 覆盖成功互动、三处管理入口、权限隔离与移动端核心流程；受影响测试、API 类型检查和完整静态构建通过后才转为已实现。
