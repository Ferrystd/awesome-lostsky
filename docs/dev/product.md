# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

LostSky 的主要用户是陪玩与数字服务工作室的运营者、团队管理员和成员。他们在手机与桌面浏览器中完成团队、成员、岗位、文档、文件和业务资料管理。官网面向希望了解 LostSky 与进入工作台的访客；团队 Display 主页面向查看团队公开资料、可展示成员、虚拟实体和公开文档的外部访客；团队 Shop 面向浏览商品、维护当前商家顾客资料并使用商家预存余额购买的顾客。

## Product Purpose

把分散的工作室运营资料和协作流程收进一个可追踪、可授权、可持续扩展的工作台，并通过官网、团队公开主页与展示型商城建立 LostSky「失落青空」及其团队的可信公开形象。

## 后台工作台入口

微博个人工作台的点单信息流是受限列表的明确例外：缺少个人使用 Permission 或微博 Ability 时，仍显示每条帖子的首尾片段，禁止打开原帖和评论；服务端不返回完整正文或可还原原帖的标识。其他列表遵循下述普通降权规则。信息流以文字和时间为主，不显示图片；团队与个人预设评论合并供手动选择，不自动评论。

Weibo 将个人使用与团队管理拆成 `weibo.personal.use`、`weibo.team.manage`。基础概览和访问快照不要求业务 Permission；业务导航、数据读取和本地管理按当前工作台 Permission 收口，只有远端发帖、点赞、评论，以及任务开启、恢复和 Worker 执行额外要求 Weibo Ability。

团队域后台顶栏固定提供黑色的“团队、商品、记账、聊天、微博”五个直达入口，并保持当前团队与当前 Entity；所有后台应用共用五等宽入口导航，不允许各应用分别定义颜色、字号、宽度、内边距或项间距。Team、Shop、Transaction 与 Weibo 的团队工作台允许本团队有效 Entity 直接进入，也允许获得目标团队至少一个角色的外部有效 Entity 进入；外部身份首次进入时先由 Account 明示当前 Entity 与目标团队，确认只抑制 24 小时提示，不改变授权。个人工作台仍要求 Entity 归属于地址团队，Chat 不开放跨团队工作。各工作台都把“概览”固定为首个导航入口，概览不因业务 Permission 消失或改绑；具体入口、读取和操作继续按 Permission 收口。

工作台入口、侧栏导航和业务页面不会因 Permission 或 Ability 消失或阻止进入。列表读取受限时页面渲染普通空列表，详情、表单和指标等普通数据受限时只把关键值显示为 `-`；受限空状态由 `LsEmptyState` 显示对应 Permission / Ability 原因，替换正常空文案；普通数据原因继续通过 `feedback.info()` 短时弹窗说明。具体受限按钮保持原有业务按钮和位置，只比正常状态更灰并保持可点击与可聚焦，用户点击后由 `LsButton` 弹出一次短时原因说明。Transaction 的登记流水入口属于个人工作台，顾客候选按当前 Entity 的归属或发单绑定范围收口；个人业绩统计合并到“我的流水”，与我的接单、我的顾客和权益下发均属于当前 Entity 本人范围，入口和读取不依赖 Team 全量 Permission；服务端始终按 `acting_entity` 固定范围。“我的顾客”合并当前归属与协作发单关系，同一顾客只显示一次并分别标明关系。顾客协作关系在 Team 顾客详情随资料统一查看和维护：读取沿用顾客可见范围，写入使用 `team.customer.manage`，不受 Transaction Ability 控制。团队“权益核销”作为 Team 全量资源入口，读取要求 `service.redemption.read` 或 `service.redemption.manage`，管理只接受后者；个人“我的接单”允许当前接单 Entity 填写核销字段并完成自己的任务，不因此取得改派、费用调整或管理他人任务的权限。后台统一始终显示真实纵向滚动条，长短页面之间切换时不得推动顶栏标题或应用导航横向跳动，也不得在右侧留下空白占位槽。`transaction` Ability 不控制“记账”应用入口、页面读取或普通管理动作，只在赋予顾客权益确认提交、顾客确认充值、登记流水保存、接受接单邀请和个人下发权益时，于用户点击后通过 `feedback.info()` 提示并阻止提交；界面不常驻展示 Ability 缺失说明。`shop` Ability 只约束面向顾客的商品陈列与购买，不关闭 Shop 后台、顾客中心或历史业务入口。

Shop 管理统一为商品和订单入口，商品分为普通商品、核销商品、卡密、套餐和多规格商品。核销配置直接随商品保存，套餐和卡密选择其他商品；不再要求建立服务、权益包或卡活动。个人范围按当前 `acting_entity` 隔离，只能组合本人或团队公用商品；团队工作台保留全量监管。

本人商品、服务与权益包服务项的分成调整统一要求 `shop.product.self.reprice`。缺少该权限时仍可调整纯本人资源的售价与成本，但人员分成沿用原值；公用服务在本人权益包中的价格、成本与分成均锁定。创建时的默认分成、分项汇总和计价冻结边界见 [Shop 应用](apps/shop.md)。

发单人可在 Transaction 从 Shop 已配置的权益套餐商品直接赋予顾客独立权益。个人工作台以“权益下发”作为稳定入口，当前 Entity 无需 Transaction Ability 即可查看自己直接下发的权益；“下发权益”动作同时要求有效的 Transaction Ability 与 `service.entitlement.grant`，且只能操作自己接待或绑定的顾客，发单人强制为当前 Entity。该动作固定不创建 Shop 订单，团队设置独立决定是否同步权益包收款流水。商品与权益资源继续由 Shop 管理，Shop Ability 不成为后台维护或直接赋予的门槛。

## Positioning

面向小型数字工作室的清晰运营底座：不把复杂度转嫁给使用者。

成员生命周期遵循“状态变化不抹去业务历史”：封禁和离队只改变登录与实体可用性，成员资料、对象标识、角色和顾客、订单、聊天、文档等关系持续保留；复职继续使用原实体。界面必须始终显示成员状态与不可用原因。

## Brand Personality

冷静、敏锐、有余韵。品牌像白昼消失后的高空：克制但并不寡淡，专业但不套用企业软件模板。

## Anti-references

展示官网保持历史陪玩运营工作室的深色、青蓝/紫色渐变与玻璃层次；账户与团队等后台不使用这些装饰性效果，也不为“高级感”牺牲可读性的低对比文字和装饰动效。

## Design Principles

- 名字就是视觉叙事：青色天光逐渐进入深空，琥珀只作为残留信号。
- 官网先建立记忆，再解释能力；后台让界面退后，让任务向前。
- 真实产品画面与媒体资产承担证明，不用抽象卡片代替内容。
- 移动端是首要工作环境，任何核心任务都不能依赖桌面宽度或悬停。
- 标准交互优先于新奇交互，个性来自构图、排版、色彩和素材。

## Accessibility & Inclusion

以 WCAG 2.2 AA 为最低目标，支持键盘、屏幕阅读器、放大文字、减少动态效果和省流量模式。颜色不作为唯一状态信号，移动端交互目标不小于 44×44px。
