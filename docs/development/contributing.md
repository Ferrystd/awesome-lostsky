## 工作区保护与阶段性暂存

暂存区用于保存“当前任务中已经确认的基线”，帮助区分已验证结果与后续修改；它不是备份、提交或完成标志，也不能阻止文件再次被覆盖。长期保留或交接仍应使用正常提交。

1. 开始任务时先运行 `git status --short` 和 `git diff --cached --name-only`，识别工作区与暂存区中已有内容；已有差异默认属于用户或其他任务，不得顺手纳入、回退或清空。
2. 只有一个切片能够独立说明、已完成直接相关验证且准备继续进行后续工作时，才建立暂存基线。长任务、上下文切换、委派、用户确认结果，以及执行可能覆盖文件的生成、恢复或批量修改前，应优先考虑暂存；尚未验证的试验代码和半成品不暂存。
3. 使用 `git add -- <明确路径>` 暂存完全归属当前切片的文件；禁止使用 `git add .`、`git add -A` 或宽泛目录把无关差异一起纳入。同一文件混有其他任务差异时，只能在确认每个区块归属后使用 `git add -p -- <路径>` 逐块暂存；不能可靠拆分时保持未暂存并先解决边界。
4. 暂存后立即运行 `git diff --cached --name-only` 和 `git diff --cached --check`，再审查 `git diff --cached -- <路径>`，确认暂存内容完整、可解释且没有凭据、生成物或无关变化。继续修改后，`git diff` 表示相对暂存基线产生的新工作区差异，`git diff --cached` 表示已确认基线。
5. 不得用 `git reset`、`git restore --staged`、`git checkout` 或等价操作清空、重建或覆盖已有暂存内容，除非用户明确授权且目标已逐项核对。发现暂存区已有无关内容时保留原状，只追加能够明确归属的区块。
6. 提交、发布或交接前重新审查暂存区；测试范围仍按当前任务实际修改的契约判定，不因文件已暂存而扩大，也不把暂存成功当作验证通过。

禁止提交凭据、Token、Cookie、个人路径和内部地址。确认但暂不处理的工作写入[待办](../TODO.md)。
