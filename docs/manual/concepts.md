# 核心概念

LostSky 把“登录的人”和“正在执行业务的主体”分开。刚接触时，最重要的是分清账号、实体、当前身份、团队能力和角色权限；这几项决定你能进入哪个团队、看到哪些资料，以及能执行什么操作。

## 一句话关系

1. **账号（User）**完成登录，记录真实用户、设备和安全会话。
2. 账号领取一个**实体（Entity）**后，该实体成为**当前身份**。
3. 地址中的团队决定当前**团队上下文**；多数团队业务要求当前身份也属于该团队。
4. 团队的 **Ability** 决定某项产品能力是否开通，实体的**角色与 Permission** 决定这个实体能否执行具体操作。
5. 对象的状态、归属和可见范围继续限制最终可见内容；“按钮出现”不等于服务端一定允许提交。

因此，“已经登录”“已经是成员”和“有权执行操作”是三件不同的事。

## 常用概念

| 概念 | 它回答的问题 | 例子 |
| --- | --- | --- |
| 账号（User） | 真实登录者是谁？ | 小林使用手机号注册的 LostSky 账号 |
| 团队（Team） | 资料和业务属于哪个工作空间？ | “青空陪玩工作室” |
| 实体（Entity） | 当前业务由谁执行、资料属于谁？ | 团队本身、成员小林、客户阿远、售后机器人 |
| 当前身份 | 这个账号此刻代表哪个实体？ | 小林登录后领取自己的成员实体 |
| 角色（Role） | 一组职责叫什么、包含哪些权限？ | “接单员”“财务”“内容管理员” |
| Permission | 当前实体能执行哪个具体操作？ | `transaction.write` 允许登记或编辑流水 |
| Ability | 当前团队是否开通某项产品能力？ | `doc` 开通团队文档，`file` 开通文件上传 |
| Slug | 如何稳定、准确地识别一个实体？ | `member-17`、`support-bot` |
| 可见范围 | 已经能打开某类资料的人还能看到哪一条内容？ | 公开文档、仅团队人员可见字段 |

Ability、Permission 的完整区别和枚举见[能力、权限与功能降级](access-and-abilities.md)，所有权限键见[权限目录](permissions.md)。

## Entity：统一的业务主体

Entity 可以理解为“可以拥有资料、接受角色、出现在引用中，或代表自己执行业务的对象”。LostSky 当前有四类团队实体：

| 类型 | 用户界面名称 | 是否直接关联真实账号 | 典型用途 | 公开规则 |
| --- | --- | --- | --- | --- |
| `team` | Team / 团队 | 否 | 团队本身作为通知收件人、角色主体或邀请归属 | 团队主页始终以团队状态为准 |
| `teamMember` | 成员 | 是 | 运营、接单、审核、管理资料和协作 | 可按团队设置进入搜索或 Display |
| `teamCustomer` | 客户 | 可以关联账号，也可以由其他实体派生 | 商家客户资料、预存余额、订单、流水和会话 | 默认团队内隐藏，永不进入公开 Display |
| `teamVirtual` | 虚拟实体 | 否 | 人工代操作、Webhook、机器人或外部工作流 | 只有有效且开启公开展示时才进入 Display |

“成员”和“客户”不是两个登录系统。真实用户仍用同一个账号登录，再领取相应实体身份。团队和虚拟实体没有自己的密码；它们只能由已获授权的实体代为操作，虚拟实体也可以通过单独的 Webhook 凭据接入 Chat。

### 三个例子

- 小林登录账号后领取“成员小林”实体。流水登记以小林当前领取的实体和角色鉴权，审计仍能追溯到小林的真实账号与设备。
- 阿远在青空工作室商城首次绑定后得到“客户阿远”实体。这个实体只属于该商家，保存该商家的昵称、余额和订单，不会生成公开客户主页。
- 团队创建“售后机器人”虚拟实体，并给运营成员授予操作权限。运营成员或配置好的 Webhook 可以代表机器人发消息，但机器人本身不能使用账号密码登录。

## 账号、根身份与委托身份

基础账号可以直接领取与本人关联且有效的成员或客户实体，这类身份是会话的根身份。领取 Team 或虚拟实体、领取其他成员或跨团队领取身份，需要目标团队通过 `identity.*.assume` Permission 明确授权。

每次切换都会让旧实体会话失效，不会把多个身份同时叠加。放弃身份则回到基础账号。无论委托多少次，真实登录账号、设备和审计链都不会被替换。

> 例：团队把 `identity.virtual.support-bot.assume` 授予成员小林。小林可以从自己的成员身份切换为 `@support-bot`；切换后业务权限按机器人实体重新计算，而不是继续沿用小林的成员权限。

## 团队上下文

Team、Chat、Transaction、Display 和 Shop 使用带团队 slug 的地址，例如 `demo.team.lostsky.work`。地址里的 `demo` 决定当前团队。

多数团队后台请求同时要求：

- 当前账号已登录；
- 已领取有效实体身份；
- 当前实体属于地址对应团队；
- 团队未被封禁；
- 所需 Ability、Permission、可见范围和资源状态均满足。

如果当前身份属于另一个团队，系统会要求确认领取地址所对应团队的本人成员身份。取消不会撤销原身份。

## Slug：稳定标识，不是显示名称

Slug 是实体的全局唯一文本标识，用于 URL、搜索、Markdown 引用、邀请来源和精确权限。界面通常以 `@slug` 展示。

- Slug 与昵称不同：昵称可以重复或变化，Slug 用于准确定位。
- 创建团队或虚拟实体时确定 slug；已经领取的 slug 不可随意修改或复用。
- 新成员通常自动取得 `member-{id}`；历史上没有 slug 的成员或客户需要先完成首次领取。
- 复制 slug 时应连同实体类型和团队核对，避免把权限或通知发给同名对象。

## 角色与权限如何作用于实体

角色是一组 Permission。角色可以分配给团队内实体，也可以通过全局 slug 分配给外部来源实体；后者只表示该来源获得当前目标团队授予的权限，不会让它直接越过团队边界读取业务数据。

一个实体拥有多个角色时，有效 Permission 取并集。LostSky 没有“拒绝权限”覆盖机制：任一角色允许即视为允许。修改或删除角色会立即影响依赖它的操作和后续身份委托。

## 三套实体发现范围

以下开关互相独立，开启一个不会自动开启另外两个：

| 范围 | 决定什么 | 谁可以越过限制 |
| --- | --- | --- |
| 团队内可见 | 普通团队实体能否在工作空间目录发现对象 | `team.entity.read` 可读取完整有效实体集合 |
| 全局可搜索 | 已登录用户能否通过 slug 在跨页面搜索中找到对象 | 由团队搜索设置和成员覆盖值共同决定 |
| 公开 Display | 未登录访客能否在公开主页看到实体 | 只显示有效且开启公开展示的非 Customer 实体 |

无权查看团队内隐藏实体时，直接链接返回“未找到”，不会泄露该对象是否存在。

## 内容的管理范围与可见范围

实体存在并不代表其所有字段和文档都可见。文档、对象字段等内容还会使用以下范围：

| 范围 | 用户可观察结果 |
| --- | --- |
| 团队管理可见 | 只有具备相应管理资格的实体可见 |
| 主体本人和团队管理可见 | 内容归属实体本人及团队管理者可见 |
| 团队人员可见 | 当前团队内有效实体可见 |
| 公开可见 | 满足公开条件后，未登录访客也可见 |
| 指定对象可见 | 团队管理者及选定实体可见 |

“可见”不等于“可编辑”。管理范围决定主体本人能否参与管理；字段的值维护范围和“允许修改字段值”还会继续限制保存。完整操作见[团队工作台](team-workspace.md)。

## 容易混淆的区别

| 容易混淆 | 正确理解 |
| --- | --- |
| 登录账号 = 当前身份 | 错。账号负责认证，当前实体负责团队业务 |
| 成员 = Entity 的全部 | 错。Team、客户和虚拟实体也是 Entity |
| Ability = Permission | 错。Ability 属于团队产品开通状态，Permission 属于实体角色授权 |
| 有 Permission 就一定能操作 | 错。仍需身份、团队、Ability、资源状态和可见范围同时满足 |
| 团队内可见 = 可公开搜索 = Display 公开 | 错。三套范围独立 |
| 公开角色会公开权限 | 错。公开角色只展示名称和说明，不展示 Permission |
