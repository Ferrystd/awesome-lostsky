# 团队工作台

Team 是团队日常协作和配置入口。团队工作台保留既有概览、实体、成员、顾客、通知、文档、文件、管理结构与页面排版；仅把概览主操作“进入消息”替换为“进入个人工作台”，并把原顶栏动作替换为“团队、商品、记账、聊天”四入口。个人工作台提供当前实体(Entity)的资料、对象字段、角色与有效权限；不在 Team 顶栏新增分段式工作台切换。向下滚动时，工作区顶栏随文档正常离开，不会覆盖表单字段或错误定位结果。

进入前应确认地址中的团队与当前实体一致。不了解 Entity、Ability 或 Permission 时，先读[核心概念](concepts.md)和[能力、权限与功能降级](access-and-abilities.md)。

## 功能基线

| 编号 | 用户目标 | 典型前置条件 | 应有结果 |
| --- | --- | --- | --- |
| TEAM-01 | 查看团队概览 | 当前团队有效 Entity | 看到访问感知的实体、成员、文档和通知摘要 |
| TEAM-02 | 维护自己的成员资料 | 当前团队成员身份 | 保存本人资料和允许本人维护的对象字段 |
| TEAM-03 | 浏览或管理实体、成员和顾客 | 基础可见范围，或对应读取/管理 Permission | 只显示当前身份有权读取和操作的对象 |
| TEAM-04 | 管理角色和 Permission | `team.role.read` / `team.role.write` | 角色、完整权限集合及实体角色分配被保存 |
| TEAM-05 | 管理对象字段 | 对应字段管理 Permission | 字段定义、值和访问规则按对象类型生效 |
| TEAM-06 | 管理文件和文档 | 对应 Permission；File / Doc Ability 按动作可用 | 内容保存到当前团队并按可见范围提供 |
| TEAM-07 | 阅读或发送通知 | Team 站内通知需读取 Permission；发送需发送 Permission | 内容进入正确收件箱并按收件 Entity 共享已读状态 |
| TEAM-08 | 申请加入团队 | 已登录且不是当前团队成员 | 申请可提交、查询，并在处理中取消 |
| TEAM-09 | 审核加入申请 | 加入审核 Permission | 申请进入审核流程，并被同意或拒绝 |
| TEAM-10 | 配置虚拟实体与 Webhook | 对应创建或 manage Permission | Chat 可使用有效虚拟实体和集成配置 |
| TEAM-11 | 配置团队策略 | `team.setting.read` / `team.setting.update` | 搜索、Chat 和商城联动按保存值生效 |
| TEAM-12 | 从工作台发起对话 | 当前身份可使用该团队 Chat | 进入团队消息页，并可预选实体、成员或顾客 |
| TEAM-13 | 管理加入申请字段 | `team.join_field.read` / `team.join_field.write` | 申请表字段、启用状态、顺序和审批后转存规则生效 |

## 概览和导航怎样降级

概览固定显示实体、成员、文档和通知。具备实体、成员或文档全量读取 Permission 时显示具体数字，否则显示进入箭头；Doc Ability 缺失时文档指标标记不可用。任一摘要接口失败只影响对应卡片，不会把失败伪装为 `0`。

`工作空间`内的基础阅读入口不会把“读取全部数据”当作页面门票。`管理`入口保持固定位置：已知缺少 Permission 或 Ability 时显示禁用原因，加载页面本身不会先发起受保护请求再弹错误。所有服务端操作仍会重新鉴权。

## 个人工作台

Team、成员与虚拟实体都可从固定“个人工作台”入口进入个人概览；旧 `/me` 仍会跳转到 `/personal/profile`。个人工作台把“概览”固定为首个导航入口，并继续提供“资料”“对象字段”“角色与权限”。个人概览主视觉与工作台侧栏的“切换身份”都前往 Account 身份页并在完成后安全返回当前页面；“进入团队工作台”返回团队概览。当前数据按 JWT 的最终叶子 Entity 读取。Team Entity 也会受字段类型、Permission 和实际业务参与关系限制。

Customer 不进入后台个人工作台，继续使用商城顾客中心。Team 团队工作台继续承担角色分配、状态、团队内可见性、全局搜索、公开 Display、文档分组、虚拟实体集成和 Webhook 等管理任务。真实账号、根身份和父级委托链不会取得当前实体的编辑权。

## 实体目录与实体资料

“实体”统一浏览 Team、成员、顾客和虚拟实体；“成员”和“顾客”则处理对应类型的专属任务。四类 Entity 和示例见[核心概念](concepts.md)。

基础可见范围如下：

| 当前权限 | 实体目录结果 |
| --- | --- |
| 没有 `team.entity.read` | 只返回有效、非 Customer 且团队内可见的 Entity |
| 有 `team.entity.read` | 返回全部有效 Entity，包括 Customer 和团队内隐藏对象 |
| 没有隐藏对象访问权但打开直接链接 | 返回“未找到”，不泄露其是否存在 |

`team.entity.profile.manage` 控制实体资料、团队内可见状态和公开 Display 状态。缺少该权限时，同一详情页以只读方式打开，入口显示“查看”。

实体详情把“团队内可见”和“公开主页展示”放在同一个“可见性设置”区域中，通过一次“保存可见性”原子提交；任一值不合法时两项都不会保存。没有修改时保存按钮不可用，后台刷新不会覆盖尚未保存的选择，离开页面前会提示确认。开关本身不显示文字，当前状态由开关位置、设置标题和辅助技术共同表达；Team 与 Customer 的固定状态仍以同一种只读开关行展示。

实体资料包括名称、头像、简介、介绍图片、介绍视频、Markdown 介绍和公开文档分组。Team、成员和虚拟实体在个人资料、成员管理和实体详情中使用同一套资料字段：媒体既可粘贴已登记 URL，也可选择本地文件；Markdown 始终使用可视化/源码/预览编辑器，并保留图片上传入口。Customer 没有公开主页，也不提供公开文档分组。

“团队内可见”“全局可搜索”“公开 Display”是三套独立范围：

- 团队内可见只决定普通团队 Entity 能否在工作空间目录发现对象；
- 全局可搜索由团队搜索设置和成员覆盖值共同决定；
- 公开 Display 只决定互联网访客能否浏览该 Entity。

开启其中一项不会自动开启其他项。

## 成员管理

成员列表可以按昵称、slug 或用户 ID 搜索，并按全部、正常、已封禁、已离队和未认领 slug 筛选。状态始终展示；只有具备 `team.member.read` 的实体能读取已封禁、已离队或团队内隐藏成员的完整资料。

| 操作 | Permission | 结果与注意事项 |
| --- | --- | --- |
| 查看基础成员 | 无全量读取要求 | 只看到有效且团队内可见的成员 |
| 查看完整集合 | `team.member.read` | 包括隐藏或封禁成员 |
| 添加成员 | `team.member.invite` | 按真实 user ID 建立成员关系 |
| 编辑、封禁、解封、设置搜索或 slug | `team.member.update` | 各项仍按成员详情返回的任务能力控制 |
| 办理离职与审核离队 | `team.member.remove` | 管理员可直接将成员设为已离队；成员自助申请仍可查询、批准或拒绝 |

成员状态分为正常、已封禁和已离队。封禁或离队不会删除任何既有数据：成员、实体、slug、资料、角色、顾客归属、订单、聊天关系、文档和历史引用都会保留。

`member.inactive_entity_available` 默认关闭。关闭时，已封禁和已离队实体不能被新选择或执行业务；开启后，有相应 assume Permission 的管理员可以代为操作并继续完整业务，成员本人仍不能直接领取旧身份。

成员本人主动离队时使用独立申请。`member.departure_mode` 可设为禁止、审核或自动：禁止模式拒绝成员自助申请；审核模式进入“离队审核”；自动模式会在提交时直接批准。具有 `team.member.remove` 的管理员在成员列表或详情中使用“离职”，确认后立即完成，不再产生待审申请。如该成员已有待审自助申请，离职会直接将该记录办结为已批准。

团队 owner 不能离队。离职或批准离队后会关闭当前任期并撤销涉及该 Entity 的会话；资料、角色、对象标识和业务关系保留，旧会话不会在重新可用、解封或复职后恢复。

已离队成员再次打开加入页时，页面自动显示复职申请。复职仍使用加入审核 Permission 和任务；批准后复用原 Member、Entity、slug、资料、角色和全部业务关系，并建立新任期。`member.reinstate_refill_join_fields` 决定是否要求重新填写加入字段；只有配置为审批后转存的字段会覆盖原 Entity 字段值。

“对话”会进入当前团队的 Chat 新会话页并预选成员。成员没有 slug 或 Entity 当前不可用时不能作为新的聊天目标；既有聊天参与关系不会因封禁或离队被删除，其他参与者仍可继续发言。

成员详情同时显示成员加入时间和加入时记录的邀请人。邀请人按全局 Entity 保存，可能来自其他团队；页面会显示其名称、slug 和来源团队。历史成员或没有有效邀请来源的成员显示“未记录”。

## 顾客管理

顾客目录使用两层范围：

- 当前实体即使没有全量读取 Permission，也能查看归属于自己的顾客；
- `team.customer.read` 可查看全团队顾客；
- `team.customer.manage` 同时包含全量读取，并允许修改资料、归属、协作发单人和封禁状态。

顾客详情显示当前商家内的昵称、头像、说明、只读 slug、余额、订单、流水摘要和协作发单人。具有顾客管理权限且满足 File Ability 的管理者可直接上传头像，也可粘贴已登记 URL；不额外要求 `file.upload`。管理者可以把顾客归属设为本团队有效 Team、成员或虚拟实体，也可以清空；还可以在同一表单中通过实体多选同步协作发单人，无需二次确认。候选项同时显示类型图标、类型标签和 slug，便于区分同名实体。归属变更只影响以后创建的订单和流水，不追溯修改历史发单业绩；协作关系的增删不修改历史流水。

协作关系的查看沿用顾客可见范围：归属实体可查看自己的顾客，`team.customer.read` 或 `team.customer.manage` 可查看全团队顾客；修改只接受 `team.customer.manage`。维护协作关系不要求 Transaction Ability 或交易 Permission，但被选中的 Entity 要实际协作记账时，仍须另行满足 Transaction Ability、对应交易 Permission 和服务端记账范围校验。

顾客详情响应暂时不完整时，页面会显示可恢复的读取错误并提示刷新，不会用缺失数据展示错误余额或保留空白页面。

封禁顾客后，已有顾客身份会话不能继续使用。顾客仍不会进入公开实体目录，页面也不会暴露用户手机号、邮箱或底层 user ID。

顾客详情可在 Chat 条件满足时发起对话；该入口不会绕过顾客状态、对象可见性或会话策略。

## 角色与 Permission

角色把一组 Permission 分配给 Entity。一个 Entity 拥有多个角色时，有效 Permission 取并集，没有 deny 覆盖。

建议按以下顺序配置：

1. 创建职责清楚的角色，确定不可变的角色标识、名称、说明和排序。
2. 进入角色详情，保存该角色的**完整 Permission 集合**；空集合表示清空。普通权限用于精确授权；需要负责整个业务范围时，展开默认折叠的“高级范围权限”，搜索并选择父级 Permission。
3. 在“实体角色分配”中按名称或全局 slug 找到 Entity，并保存其**完整角色集合**。
4. 用目标 Entity 重新进入相关页面验证。

高级范围会显示当前覆盖的叶子数量和清单。选择父键会移除草稿中已被覆盖的子键，被覆盖项随即禁用；取消父键不会自动恢复此前子项。保存本次新增的父键前必须再次确认范围。父键会自动包含未来新增的同前缀权限，因此只应授予确实负责整段业务的角色；界面不允许手输目录外键。“高级范围权限”内部的“实体委托”小节用于配置委托相关父键。

身份领取与指定实体 assume Permission 统一在“实体委托”中配置；虚拟实体维护位于“实体管理”，代表虚拟实体参与聊天位于“聊天”。配置实体管理或委托时，先按名称或 slug 选择当前团队实体，再勾选适用权限；选择实体本身不会自动授予权限。Chat 组会按真实 slug 列出当前团队虚拟实体的代聊天权限。具体 key 的目标段始终使用所选 Entity 的全局 slug，不会用 `virtual` 等类型名称代替。

打开角色或权限摘要只会读取现有记录，不会清理数据。点击“保存权限”时，官方前端才会移除被父键或 `*` 权限覆盖的子键和指定 slug；服务端为兼容旧顾客端与第三方调用，会保存所有不同且合法的键。

拥有 `team.role.write` 的管理员可以授予当前团队目录中的任意高级范围，即使自己没有对应业务 Permission；成员编辑页仍只分配角色，不提供成员直授。

角色可以分配给任意团队的有效 Entity，但 Permission 始终属于当前目标团队。外部来源 Entity 不能直接越过 Team 归属边界；它只能按 assume Permission 领取目标身份后再操作。

角色的“公开展示”只让已公开 Entity 在 Display 展示角色名称和说明，不公开角色标识、Permission 或绑定记录，也不会增加或减少授权。

删除角色会使对应 Permission 和绑定失效。修改 owner 或恢复角色前，应确保至少还有一个 Entity 能管理角色。角色摘要中的“实体委托”与其他权限组平级，相关父键仍标记为“高级范围”；同一键来自多个角色，或父级/通配权限与其覆盖的子权限同时存在时，都会按存储记录完整显示。完整键和用途见[权限目录](permissions.md)。

## 对象字段

对象字段为团队定义结构化扩展资料，分为人员、顾客和虚拟实体三类。创建后，对象类型和字段标识不可随意改变。

### 值类型与输入控件

| 值类型 | 适合内容 |
| --- | --- |
| `string` / `text` | 短文本 / 长文本 |
| `int` / `decimal` | 整数 / 小数 |
| `bool` | 是/否 |
| `date` / `datetime` | 日期 / 日期时间 |
| `select` / `multi_select` | 单选 / 多选；选项每行一个 |
| `json` | 需要结构化保存的高级数据 |

输入控件可选择 `text`、`textarea`、`radio`、`checkbox`、`select`、`date` 或 `datetime`。值类型、控件和选项应保持匹配，否则用户可能无法按预期填写。

### 维护与可见规则

| 配置 | 作用 |
| --- | --- |
| 仅字段管理员维护 | 对象本人不参与写入 |
| 对象本人和字段管理员维护 | 本人可在已有用户界面支持的资料页参与维护 |
| 仅字段管理员可见 | 只有具备对应字段管理 Permission 的 Entity 可见 |
| 对象本人和字段管理员可见 | 额外允许字段所属对象本人查看 |
| 团队实体可见 | 当前团队有效 Entity 可见 |
| 公开可见 | 所属 Entity 有效且已开启公开主页时，未登录访客也可见 |
| 指定对象可见 | 额外允许选定 Entity 查看 |

可见范围只过滤已经有权打开的资料，不额外授予页面或接口访问权；可见也不等于可编辑。“允许修改字段值”关闭后，字段管理员和对象本人都只能查看。删除字段会同步删除该字段在全部对象上的值，应先确认数据不再需要。

Team、成员或虚拟实体本人在 Team 个人工作台“对象字段”维护允许本人编辑的字段，团队管理员继续在成员/实体管理流程维护管理范围内字段。Customer 在商城顾客中心维护顾客资料，不进入该入口。字段值搜索尚未开放，“允许搜索”类历史配置不参与当前可见性判断。

## 文件

“文件”页用于查看、搜索、上传和按 Permission 删除团队空间文件。文件以当前团队为边界，并记录上传 Entity。

上传同时要求：

- File 0 级或更高等级的容量尚未用尽；
- 当前实体具有 `file.upload`；
- 单文件不超过 50 MiB；
- 扩展名在允许列表中。

支持的扩展名包括：

```text
jpg jpeg png gif webp avif
mp4 webm mov mp3 wav ogg m4a
pdf txt md csv json
doc docx xls xlsx ppt pptx
zip 7z rar
```

`file.read` 控制文件列表和用量，`file.delete` 控制删除。文件数量不限制；没有 File Ability 记录时按 0 级 128 MiB 计算，升级后依次使用 1/2/3 级容量，见[能力、权限与功能降级](access-and-abilities.md)。删除会先永久删除 OSS 对象，成功后再永久删除文件记录并立即释放容量；OSS 删除失败时记录和已用容量保持不变，文件不提供回收期。

`file.upload` 只控制“文件”页上传到团队文件库。资料头像、商品封面、介绍媒体、对象字段文件和 Markdown 图片属于各自资源附件：上传只要求团队容量未用尽，最终保存仍由资料、商品、文档、通知或对象字段的既有编辑权限校验。团队未购买 File Ability 时使用 0 级 128 MiB；容量用尽后，所有资料上传按钮和 Markdown 编辑器原有的本地图片上传图标保持可见但不可上传。外部图片 URL、已有文件读取和文档编辑仍可使用。

## 文档

文档功能整体要求 Doc Ability。文档可以归属于当前团队任意有效 Entity，并包含标题、Markdown 正文、管理范围、可见范围、指定对象、排序和标签。

没有 `team.document.read` 时仍可进入文档页，但只看到当前实体按可见范围可读的文档；具备该 Permission 后可读取全团队文档。创建、编辑和删除由 Doc Ability、文档管理范围、归属主体和当前实体共同判断，不存在统一的 `team.document.write` Permission。

### 文档标签

标签是独立资料，不从 Markdown 标题或 `#标签` 解析：

- 在文档表单中用“添加标签”逐项填写，无需输入 `#`；
- 标签去除首尾空白，保留大小写和当前顺序；
- 标签不能为空、不能以 `#` 开头、不能含控制字符，最多 50 个字符；
- 同一文档内不能出现完全相同的重复标签；
- 可拖动排序，也可使用上移、下移按钮完成同一操作。

实体资料页可以按顺序配置“公开文档分组”，每项由标签和可选说明组成，说明最多 255 个字符。Team、成员和虚拟实体支持分组，Customer 不支持。没有实体资料管理 Permission 时可以查看现有分组，但不能修改。

Display 只按完全相同的标签文字匹配，大小写不会合并；同一文档匹配多个分组时会出现在多个分组中。未命中配置标签的文档继续出现在“公开文档”，空分组不显示。标签不改变正文、可见范围、搜索、排序或授权。

缺少 Doc Ability 时文档导航禁用，直接打开文档列表、创建、编辑或详情会返回概览并提示原因。已经公开的文档不会因此自动从 Display 撤下；如需撤下，应在能力有效时修改可见范围，或联系平台管理员恢复能力后处理。

## 通知与站内通知

Team 有两种单向通道：

| 界面名称 | 发送方与收件方 | 查看要求 | 发送要求 |
| --- | --- | --- | --- |
| 通知 | 当前有权限的 Entity 代表 Team，发给同 Team 一个 Entity | 当前实体收件箱无需额外 Permission | `team.notice.send` |
| 站内通知 | LostSky 发给 Team 的共享通知 | `team.notice.read` | 当前版本没有 LostSky 在 Team 界面直发 Entity 的入口 |

通知可以发送给 Team、成员、顾客或虚拟实体，界面统一显示 Team 为发送方；真实操作者和登录账号保留在业务审计。每条通知的已读状态由收件 Team 或 Entity 共享，同一 Entity 被不同账号代操作时看到同一已读结果。

通知不支持回复、抄送、会话或跨 Team 投递，也不等同于 Chat。接口保留的“收取通知资产”动作当前未实现，不应当作可用附件领取流程。

## 审计日志

具有 `team.audit.read` 的 Entity 可以从 Team 管理导航进入“审计日志”。没有权限时入口保留为禁用状态并说明缺少的 Permission；直接请求接口会返回 403。

列表首屏保留关键词和应用筛选；动作、资源类型和时间范围收进“更多筛选”，存在已选高级条件时按钮显示数量。筛选目录覆盖实际写入的动作与资源类型，包括领取、确认、重新发起、服务实例和履约加价费用；未知历史值仍按原值显示。列表分页查看成功完成的管理操作。打开单条记录后可查看认证账号、实际 acting Entity、目标、发生时间、请求 ID、是否真正产生变化，以及允许留存的字段差异。幂等命令可能显示“命令成功但状态未变化”。

审计详情不会保存或展示正文、Markdown、联系方式、带参数 URL、Token、签名密钥或 Webhook 密钥的原值，只会说明相关字段发生过变更。失败请求、通知已读、普通聊天消息和预检请求不出现在业务审计中；排障时使用详情中的 `request_id` 联系运维人员查询系统运行日志。审计记录保留 730 天，当前不提供 CSV 导出。

## 申请加入与审核

非成员访问团队加入页后，可以读取当前申请表单、填写资料和备注并提交。一个账号在同一团队只能有一条“已申请”或“审核中”的活动申请；取消、拒绝后可以重新申请。

链接中的 `ref` 会按与顾客邀请相同的 `inviter_slug` 参数随申请提交。仅当链接带有有效邀请参数时，表单才在提交前只读显示当前邀请人，申请人不能在页面内修改；未带邀请参数时不显示邀请人区域，页面与普通加入申请一致。有效的 Team、成员或虚拟实体都可以成为邀请人，并允许来自其他团队。无效、已失效或 Customer slug 会被忽略。

| 状态 | 数值 | 用户可观察结果 |
| --- | ---: | --- |
| 已申请 | 1 | 已提交，等待审核；申请人可取消 |
| 审核中 | 2 | 审核人员正在处理或维护任务；申请人仍可取消 |
| 已取消 | 3 | 申请人主动终止，本次流程结束 |
| 已加入 | 4 | 已创建或关联成员 Entity，团队会出现在“我的团队” |
| 已拒绝 | 5 | 审核未通过，本次流程结束并保留拒绝说明 |

具备 `team.join_field.read` 的 Entity 可以进入“申请字段”，搜索并查看启用或停用字段；具备 `team.join_field.write` 后可以创建、编辑、停用、重新启用和删除字段。字段可配置名称、稳定标识、值类型、输入控件、选项、默认值、是否允许填写、是否必填及排序。字段标识创建后不能修改；已经产生提交记录的字段不能删除，应改为停用，历史申请仍保留原值。

选项字段分别保存给申请人看的“显示名称”和实际提交的“提交值”。审批后转存可以选择当前团队的人员对象字段，不要求操作者同时取得对象字段管理 Permission；目标字段的名称、标识和值类型会在选择时显示，保存时服务端仍重新确认团队归属。

具备 `team.join_review.read` 的 Entity 可以查看申请，具备 `team.join_review.write` 的 Entity 可以开始审核、维护任务、标记任务完成、同意或拒绝。审批通过时系统创建成员及默认 slug，并把申请时确认的邀请人写入成员；配置为“审批后转存”的申请字段会写入对应 Entity 字段。申请阶段上传文件仍要求 File Ability 和文件规则。

## 虚拟实体与 Webhook

虚拟实体用于人工代操作、Webhook、机器人和外部工作流。创建需要 `team.entity.virtual.create`；编辑、删除和集成管理需要 `team.entity.virtual.<slug>.manage` 或通配权限。仅在 Chat 中代表虚拟实体参与会话使用 `chat.virtual.<slug>.act` 或通配权限；它不会切换身份，也不能授权其他应用。

创建虚拟实体时设置稳定 slug、名称和资料。之后可添加多个 Webhook 集成，配置名称、有效 HTTPS 地址、订阅事件和启用状态。Webhook 地址不能指向内网或保留地址。

集成创建或轮换后会显示 API Token 和签名密钥，明文只出现一次：

1. 立即复制到受控的密钥管理位置；
2. 不要粘贴到文档、聊天、工单截图或前端代码；
3. 轮换后旧凭据立即失效，应同步更新外部系统；
4. 不再使用时禁用或删除集成。

Webhook 只代表所属虚拟实体，只能向该虚拟实体已经参与的会话发送消息，不能替代用户登录或任意领取身份。

## 团队设置

“团队设置”按应用分组展示。`team.setting.read` 可查看，`team.setting.update` 可保存；每个分组独立保存。

### 对象搜索

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| 团队自身可搜索 | 关闭 | 允许已登录用户通过 `@slug` 找到 Team |
| 成员默认可搜索 | 关闭 | 成员没有个人覆盖值时采用该值 |
| 搜索优先级 | 团队优先 | 团队优先：团队关闭时成员均不可搜索；成员优先：成员显式设置可覆盖团队默认值 |

### Chat

| 设置 | 默认值 | 范围与枚举 |
| --- | --- | --- |
| 顾客可发起单聊 | 开启 | 允许顾客主动联系团队公开且可用的成员或虚拟实体 |
| 顾客群聊权限 | 仅限团队邀请 | 禁止顾客加入 / 仅限团队邀请 / 允许顾客创建 |
| 新成员可见群历史 | 仅加入后消息 | 仅加入后消息 / 全部历史消息 |
| 显示已读回执 | 开启 | 关闭后不推进或展示参与者已读游标 |
| 消息编辑窗口 | 15 分钟 | 0–1440；0 表示本人不能编辑 |
| 消息撤回窗口 | 2 分钟 | 0–1440；0 表示本人不能撤回 |
| 消息保留天数 | 0 | 0–3650；0 表示永久保存，正数由清理任务删除到期消息内容 |

“允许顾客创建”表示顾客可以创建群聊，但不能主动邀请其他顾客；“仅限团队邀请”表示顾客不能创建群聊，只能由团队成员邀请；“禁止顾客加入”同时禁止创建和被邀请。

### 商城

“开放商城”是顾客商品陈列与购买的总开关，默认关闭。团队拥有有效的 Shop Ability 后才能开启；Ability 缺失、等级不足或到期时，滑块会以禁用样式显示，点击后说明原因且不能开启，关闭操作始终可用。Shop Ability 完全失效后，系统会自动关闭该设置，并向团队发送一条站内通知；能力恢复后仍需管理员手动重新开启。

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| 自动同步记账流水 | 开启 | 下单时生成关联流水，但只有 Transaction Ability 有效时才真正同步 |

关闭自动同步或 Transaction Ability 不可用时，商城订单、预存余额扣减和取消退款仍正常，只是不生成关联流水。

### 公开主页

| 设置 | 默认值 | 作用 |
| --- | --- | --- |
| 主页欢迎语 | 欢迎来到我们的公开主页 | 团队公开简介为空时显示在 Display 主页首屏 |
| 实体入口文案 | 浏览公开实体 | 主页首屏跳转到公开实体预览的链接文字 |
| 实体区域标题 | 公开实体 | 主页实体预览区域的标题 |
| 实体区域说明 | 团队成员与虚拟实体 | 主页实体预览区域的辅助说明 |
| 实体空状态文案 | 团队暂时没有公开实体 | 主页没有可公开实体时的提示 |

这五项只改变团队 Display 主页的展示文案，不改变公开范围、实体目录筛选、Permission 或 Ability。每项必须填写 1–100 个字符。

## 当前边界与恢复

- 所有管理操作由服务端重新校验；界面隐藏或禁用按钮不是授权机制。
- 缺少当前身份时进入 Account；身份属于其他团队时必须明确确认切换。
- 私有内容、隐藏 Entity、跨团队对象和无效对象不会因为知道链接而开放。
- 页面数据会在重新进入、窗口重新聚焦和操作完成后自动更新；不要用连续重复提交代替确认结果。
- 集合页没有数据或筛选无结果时会显示当前情况和下一步；先清空搜索和筛选，再判断是否为可见范围问题。
- 桌面顶栏显示完整操作，移动端使用“操作”或“更多”菜单；移动端收起不表示功能被删除。
- Ability 和 Permission 的责任人不同。恢复方式见[能力、权限与功能降级](access-and-abilities.md)和[问题排查](troubleshooting.md)。
