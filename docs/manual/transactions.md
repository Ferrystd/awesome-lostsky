# 记账与顾客余额

Transaction 用于团队经营记录。所有金额、顾客、参与 Entity、余额和顾客协作范围都以当前团队为边界。Transaction 不是银行账户或第三方支付工具；“余额”是商家在 LostSky 内维护的顾客预存余额。

## 功能基线

| 编号 | 用户目标 | 典型前置条件 | 应有结果 |
| --- | --- | --- | --- |
| TRANS-01 | 查询团队全部流水 | Transaction Ability、`transaction.read` | 可筛选列表并查看当前团队流水详情 |
| TRANS-02 | 新建或编辑流水 | Transaction Ability、`transaction.write`，且满足记账主体范围 | 平衡金额、参与方和余额变动在同一操作中保存 |
| TRANS-03 | 删除手工流水 | Transaction Ability、`transaction.delete` | 流水删除，已消费预存余额安全退回 |
| TRANS-04 | 查看团队经营统计 | Transaction Ability、`transaction.report.read` | 按时间得到摘要、趋势、接单人、顾客和归属业绩 |
| TRANS-05 | 使用顾客协作关系扩展记账范围 | Team 顾客详情已配置协作发单人；实际记账仍需 Transaction Ability 与对应 Permission | 被配置的 Entity 可在合法记账范围内协作处理顾客 |
| TRANS-06 | 查询顾客余额 | Transaction Ability、`transaction.read` | 查看可用余额、累计充值/消费及完整变动日志 |
| TRANS-07 | 为顾客充值 | Transaction Ability、`transaction.write` | 余额与充值日志在同一操作中更新 |
| TRANS-08 | 手动赋予顾客权益 | Transaction Ability、`transaction.write`，Shop 已有可用服务套餐商品 | 顾客获得独立权益且不创建订单；团队设置决定是否同步收款流水 |
| TRANS-09 | 查看团队归属业绩 | Transaction Ability、`transaction.report.read` | 按流水创建时的归属快照统计顾客数、流水数和金额 |
| TRANS-10 | 使用个人记账工作台 | 当前 Team、成员或虚拟 Entity，Transaction Ability | 流水、业绩、核销、绑定和赠送记录只按当前 Entity 的业务关系显示，不要求 Team 全量 Permission |
| TRANS-11 | 查看本人权益下发记录 | 当前 Team、成员或虚拟 Entity，Transaction Ability | 查看当前 Entity 直接下发的全部权益，不显示其他发单人记录 |
| TRANS-12 | 为本人接待顾客下发权益 | Transaction Ability、`service.entitlement.grant`，且顾客归属或绑定当前 Entity | 从“权益下发”页进入独立任务，发单人固定为当前 Entity，不创建订单 |

Transaction Ability 缺失时“记账”应用入口仍可见但禁用。直接打开普通记账地址只读取访问快照并显示不可用说明，不请求流水、统计、核销列表、我的顾客或余额接口。唯一业务例外是收口已经开始的履约：具备 `service.redemption.manage` 的 Entity 仍可提交“确认已核销”，但不会生成或后补流水。其他 Ability 降级见[能力、权限与功能降级](access-and-abilities.md)。

个人工作台把“概览”固定为首个导航入口；个人业绩统计与参与流水统一放在“我的流水”，我的接单、我的顾客和权益下发保持为独立业务入口。“我的顾客”合并当前归属与协作发单顾客，同一顾客只显示一次并分别标明关系。这些入口及本人范围读取都不做业务 Permission 鉴权；`transaction.read`、`transaction.report.read` 等读取 Permission 只控制 Team 全量资源。只有列表页中的“下发权益”按钮及下发任务要求 `service.entitlement.grant`。个人工作台不提供 Entity 选择器，也不会把 Entity ID 发送给个人范围接口。服务端始终从当前 `acting_entity` 派生范围；即使拥有团队全量 Permission，个人模式也不会显示其他 Entity 的数据。

团队和个人工作台的基础概览不要求业务 Permission；两者都把“概览”固定为首个导航入口。个人概览以当前 Entity 名称为主标题，并同时说明类型与所属团队；全部本人相关读取入口始终可进入。团队工作台按“团队流水、经营统计、权益核销、顾客余额”的顺序提供 Team 范围入口，缺少所需 Permission 时禁用并给出原因；个人“登记流水”入口缺少 `transaction.write` 时禁用并说明原因。其中“权益核销”入口（服务核销功能）、列表和详情要求 `service.redemption.read` 或 `service.redemption.manage`，核销管理动作只接受 `service.redemption.manage`。缺少 Transaction Ability 时仅保留不可用说明与应用切换；已开始履约的完成请求按上一段例外处理。

记账顶栏与 Team 工作台一致：桌面直接显示团队、商品、记账和聊天，移动端收进“操作”菜单，不显示应用下拉或个人/团队分段控件。团队概览以“进入个人工作台”进入个人概览；个人概览以“进入团队工作台”返回团队概览。向下滚动时顶栏随文档离开，不覆盖表单控件。两边概览只读取访问快照，不请求流水、统计、核销、我的顾客或余额数据。

## 流水类型

| 类型 | 数值 | 来源与操作边界 |
| --- | ---: | --- |
| 商城下单 | 1 | Shop 在联动条件满足时自动创建；不能在 Transaction 单独编辑或删除，应操作对应订单 |
| 记账登记 | 2 | 用户从“登记流水”创建；可按 Permission 和 Ability 编辑或删除 |
| 服务包收款 | 3 | 服务套餐订单或开启同步的手动权益赋予生成；不计为履约业绩 |
| 服务核销 | 4 | 服务完成时生成，以服务权益而非现金表达履约与分成 |
| 履约加价收款 | 5 | 顾客确认加价时生成，单独计入收款 |
| 履约加价业绩 | 6 | 主履约完成时生成，不重复计入现金收入 |

类型用于区分来源，不等于支付方式。现款和预存款在同一条流水中分别记录。

## 查看和筛选流水

流水列表按交易时间倒序显示，可以按关键词、时间、类型、接单人、发单人、客服和顾客筛选。关键词主要匹配顾客资料。

进入详情后可以查看参与 Entity、顾客、总价、支付构成、成本与分成、交易时间和备注。个人“我的流水”只显示当前 Entity 作为接单人、发单人或客服参与的记录，不要求 `transaction.read`；Team 全量流水与完整团队 Entity、顾客选项仍要求 `transaction.read`。选项出现不代表提交一定通过，服务端仍会检查对象状态和团队归属。

“我的流水”顶部同时显示六项本人统计：总接单数、总发单数、总接待数、月度业绩、月度流水和个人业绩。前三项分别计算当前 Entity 作为接单人、发单人或客服参与的业绩流水笔数，普通商品流水与每次服务核销各算一笔；服务包收款和履约加价收款属于纯收款流水，不重复计数。月度业绩是当月本人接单流水的业绩金额，月度流水是当月本人参与流水实际形成的现款与预存款收入，个人业绩是本人全部接单流水的累计业绩金额。

## 登记一条平衡流水

进入个人工作台的“我的流水”，选择“登记流水”，按四组信息填写。团队全量流水页不再提供登记入口。

### 参与方

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 接单人 | 是 | 当前团队有效 Entity；创建后不可更换 |
| 发单人 | 否 | 未选择顾客或顾客没有归属时默认当前 Entity；有顾客当前归属时默认并优先写入该归属 |
| 客服 | 否 | 顾客有当前归属时默认当前 Entity |
| 顾客 | 使用预存款时必填 | 当前团队顾客；用于余额消费、归属快照和顾客统计 |

Team、成员、顾客和虚拟实体可以作为业务参与 Entity，但具体候选和业务含义由团队流程决定。Customer 本身不能成为“邀请归属人”。
这些默认值用于减少重复填写，不锁定字段；同一 Entity 可以同时作为接单人、发单人和客服。选择顾客后仍可手动调整，提交时服务端会再次按顾客当前归属校准发单人。

### 金额必须同时满足两条等式

```text
总价 = 现款 + 预存款
总价 = 成本 + 接单人分成 + 发单人分成 + 客服分成 + 团队分成
```

所有金额必须大于或等于 0，最多两位小数。表单显示“金额平衡”后才可保存。使用预存款时，顾客可用余额必须不少于预存款金额。

### 记账主体范围

即使 Ability 和 `transaction.write` 均满足，当前 Entity 还必须符合以下任一情况：

- 当前身份就是 Team Entity；
- 当前顾客归属于该 Entity；
- 当前 Entity 已通过“发单绑定”关联该顾客；
- 新建的是没有顾客的匿名/到店流水。

编辑既有流水不能依靠“匿名顾客”规则绕过范围。无权维护该顾客时，系统会拒绝保存。

### 保存结果

保存成功后进入流水详情。若使用预存款，流水与顾客余额扣减、消费日志在同一数据库事务中完成；任一步失败都不会只保存其中一部分。

当选项接口暂时没有返回 `entities` 或 `customers` 时，表单仍会显示，但只禁用受影响的参与方、顾客或预存款字段。不要把缺失选项当作空团队后强行提交。

## 编辑和删除流水

编辑记账登记流水时：

- 接单人不可更换；
- 顾客、发单人、客服、金额、时间和备注可在允许范围内修改；
- 增加预存款会继续扣减顾客余额，减少预存款会退款；
- 更换顾客会先退回旧顾客已使用预存款，再从新顾客扣减；
- 顾客有当前归属时，发单人优先使用该归属。

删除记账登记流水时，系统会退回该流水消费的预存余额并写入退款日志，再删除流水。商城订单流水不能单独编辑或删除，必须通过 Shop 订单取消/完成流程处理，避免订单、余额和流水失去一致性。

## 经营统计

统计页使用同一日期范围展示：

- 成交金额、流水笔数和平均单价；
- 现款、预存款和成本汇总；
- 每日成交趋势；
- 接单人分成排行；
- 顾客贡献排行；
- 归属业绩中的成交顾客、流水、成交额、成本和团队所得。

统计权限与普通流水读取分开。拥有 `transaction.read` 不代表能查看经营统计；统计还需要 Transaction Ability 和 `transaction.report.read`。

归属业绩按流水创建时写入的 `sender_entity_id` 快照统计。顾客数是所选时间范围内发生交易的去重顾客数；后来修改顾客当前归属不会追溯改变历史报表。

经营统计页当前不提供生成或复制含邀请人参数链接的入口。已有链接中的合法 `ref` 仍按既有规则兼容处理，不会覆盖已经绑定的顾客归属。

## 当前归属与发单绑定的区别

| 关系 | 数量 | 主要作用 |
| --- | --- | --- |
| 顾客当前归属 | 每个顾客最多一个，可为空 | 新订单或流水优先快照为发单人，并用于归属业绩 |
| 发单绑定 | 一个顾客可绑定多个发单 Entity | 扩展哪些 Entity 可以在自己的顾客范围内协作和记账 |

协作发单人不会替代顾客当前归属。同一顾客可选择多个协作 Entity，但同一 Entity 与顾客不能重复绑定；解除关系不修改历史流水，也不清空顾客当前归属。

个人工作台的“我的顾客”同时收录当前归属和发单绑定顾客。两种关系都存在时只显示一条顾客记录，并同时显示“当前归属”和“协作发单”；搜索、分页与结果范围全部由当前 `acting_entity` 固定，不接受 Entity ID。该页面只用于查看本人顾客范围，不允许修改顾客资料、归属或协作名单。

团队侧在 Team 顾客详情查看协作关系：可见性沿用顾客范围，修改需要 `team.customer.manage`，通过实体多选随顾客资料一次保存且无需二次确认。维护关系不要求 Transaction Ability 或交易 Permission；被选中的 Entity 实际查看“我的顾客”或执行记账时，仍分别受到个人工作台范围、Transaction Ability 和对应交易 Permission 约束。

## 权益下发

个人工作台的“权益下发”入口先打开本人下发记录，显示当前 Entity 作为发单人直接下发的全部权益，包括顾客、来源商品、服务权益、下发与剩余额度、状态、下发时间和有效期。商城订单或卡密发放的权益不属于本人直接下发，不进入该列表。列表本身不要求业务 Permission；缺少 `service.entitlement.grant` 时仍能查看记录，但“下发权益”按钮不可用并说明原因。

团队管理者可在“服务核销”页选择“赋予顾客权益”；具备 `service.entitlement.grant` 的发单人可在个人“权益下发”页选择“下发权益”。两种入口复用一个单列表单：

1. 选择 Shop 中已启用的服务套餐商品；普通商品、权益卡密商品和停用商品不会出现在候选中。
2. 选择顾客和赋予份数。团队入口中 Team Entity 可选择全部有效顾客，成员和虚拟 Entity 只看到当前归属或发单绑定的顾客；个人入口始终只显示当前 Entity 归属或发单绑定的顾客。每一份都会复制商品关联权益包内的全部服务权益。
3. 团队入口核对发单人和可选客服，顾客已有当前归属时优先使用该归属；个人入口不显示发单人选择，服务端固定写入当前 Entity，不能通过请求改成他人。
4. 提交后查看结果提示中的权益项数和流水状态。

这条路径不创建 Shop 订单，也不扣顾客预存余额。权益直接归 Customer 根 Entity，并保留来源商品、发单人、客服、金额与分成快照。团队设置“手动赋予权益时同步流水”默认关闭：关闭时只生成权益；开启且 Transaction Ability 有效时，系统按商品价与份数同时生成一笔“服务包收款”。商品和权益包仍在 Shop 后台维护，Shop Ability 只决定公开商城是否开放，不阻止后台维护或本任务读取商品快照。

## 顾客余额与充值

“顾客余额”展示：

- 当前可用余额；
- 累计充值；
- 累计消费；
- 按时间排列的余额变动明细。

余额日志类型为：

| 类型 | 数值 | 常见来源 |
| --- | ---: | --- |
| 充值 | 1 | Transaction 手工充值 |
| 消费 | 2 | 流水预存款支付或 Shop 下单 |
| 退款 | 3 | 删除/修改流水、取消订单 |
| 手动调整 | 4 | 历史或运维调整；当前界面没有单独调整入口 |

充值要求正数金额、Transaction Ability 和 `transaction.write`。成功时余额与日志同时更新；失败时不会只改动一边。商城顾客不能在线充值，需联系商家由具备权限的 Entity 操作。

## 商城联动

Shop 的“自动同步记账流水”设置默认开启，但只有 Transaction Ability 等级至少为 1 且未过期时，新订单才生成类型为“商城下单”的关联流水。

“手动赋予权益时同步流水”是独立设置，默认关闭，不继承订单同步开关。它只控制直接赋予权益时是否生成“服务包收款”，不会让该动作产生 Shop 订单。

联动不可用时：

- 订单仍会创建；
- 顾客预存余额仍会扣减；
- 取消订单仍会退款且只退款一次；
- 订单和余额日志的关联流水 ID 为空；
- Transaction 统计不会出现这笔未同步订单。

这是一种明确的功能降级，不表示 Shop 下单失败。

## 常见失败与恢复

| 现象 | 原因 | 恢复 |
| --- | --- | --- |
| 记账整体显示不可用 | Transaction Ability 缺失、等级不足或过期 | 联系平台管理员恢复 Ability；期间不会读取流水、核销列表、绑定或余额，已开始履约仍可由有管理权限者完成但不记流水 |
| 只能查看，不能登记/编辑/删除 | 写/删 Permission 缺失 | 核对错误中的 Permission |
| 表单提示金额未平衡 | 两条金额等式至少一条不成立 | 重新核对支付和分成合计 |
| 预存款字段不可用 | 顾客选项缺失，或尚未选择顾客 | 等待选项恢复并选择顾客 |
| 余额不足 | 顾客余额小于预存款金额 | 先由授权 Entity 充值或改用现款 |
| 无权执行记账 | 当前 Entity 不是 Team、顾客归属人或绑定发单人 | 调整归属/绑定，或切换合法身份 |
| 个人工作台不能赋予权益 | 缺少 `service.entitlement.grant`，或顾客不属于当前归属/发单绑定范围 | 授予专用 Permission，并核对顾客归属或发单绑定 |
| 商城流水无法编辑/删除 | 它由订单联动生成 | 回到订单流程操作 |
| 报表空但存在订单 | 时间范围不匹配，或订单未同步为流水 | 核对日期和商城联动条件 |

## 当前边界

- 当前身份必须属于地址对应团队，不能凭其他团队角色直接读取数据。
- 页面允许选择的对象不代表最终授权，提交时仍重新校验 Entity、顾客、余额、Permission 和团队归属。
- Transaction 只记录团队经营数据，不执行银行卡充值、收单、提现或第三方支付。
- 列表数据会在进入、窗口重新聚焦和操作后更新；写入结果不确定时先核对详情，避免重复提交。
- 完整访问错误见[问题排查](troubleshooting.md)。
